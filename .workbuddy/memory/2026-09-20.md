### 本轮最有价值的三个发现

1. **实测替换算**：工具定义的 token 成本**不要用字符数除系数估**——
   同一条 payload 发两次、只切换有没有 `tools`，读上游 `usage.prompt_tokens` 求差。
   实测（7B）：无工具 45 / 4 工具 613 / 27 工具 **2277**；4→27 多花 **1664 token/次**
   （边际 72.3/工具）。**自检**：同 payload 连发 3 次，prompt_tokens 逐次完全相等。
   同时**主动拆掉自己的虚高陷阱**：「占 92.7%/98%」是短 prompt 的产物（探测器其余
   部分只有 45 token），**绝对增量才可迁移**，占比必须同时给分母。
2. **`model mismatch` 的代价是双向的**：同 harness / 同任务 / 同工具清单，
   3B 命中 **0/6**、7B **4/6**，而 3B **prompt_tokens 更高**（30,548 > 28,516，
   多跑一轮多调一次工具）。**换小模型既贵又不准。** 失败原因是具体行为：
   把 `prefix` 传成 `{'path: ': ...}`（**值对、键名错**），独立复现 TSCG 结论。
   处置顺序很重要：**先把自己的错误信息改成可行动的，再去看模型能不能自修**
   ——反过来就是拿模型的锅盖自己的 bug。
3. **`reset_for_test()` 声明与实现不符**（既有缺陷，本轮撞出来）：OTel 的
   TracerProvider 是**进程级单例**，`set_tracer_provider` 第二次被忽略 →
   清缓存后新建的 provider 不生效，span 仍导进**旧** exporter，而
   `get_in_memory_exporter()` 返回**新** exporter → 测试**看起来在验证，其实
   什么都没验证**（当时表现是一个 IndexError，真凶是不一致）。
   **通用教训：「静默不验证」只能靠身份断言抓，数值断言抓不到。**

### 本机环境坑（新增，值得跨会话复用）

- **系统代理拦 localhost**：`curl http://localhost:11434/api/tags` 返回 **502**
  是**代理**报的错，不是 Ollama 报的错。httpx 必须 **`trust_env=False`**。
  Bash 里探活加 `--noproxy '*'`（这样拿到的 000 才是"服务真没起"）。
- **`uv run python` 看到的 `/tmp` 不是 Git Bash 的 `/tmp`**：Bash 里 `> /tmp/x.txt`
  落在 `C:\Users\10393\AppData\Local\Temp\x.txt`，但 Python 里 `Path('/tmp/x')`
  会去找 `C:\tmp\x`。**从 Bash 传路径给 Python 要用 Windows 原生绝对路径。**
- **Bash 里连 `grep` / `head` / `tail` / `sed` 都没有**（WorkBuddy shim 覆盖 PATH）：
  统计行数用 `uv run python -c` 代替，读文件用 Read 工具。
- **`ruff format --check` 不是门禁**：本仓库 75 个既有文件都会被重排，CI 只跑
  **`uv run ruff check .`**（`pyproject.toml` 无 `[tool.ruff.format]`）。别顺手格式化。

### 流程教训

- **提交自洽性**：我第一版把 `tests/test_contextbudget.py` 和它的依赖包拆进了
  两个提交 → 那个中间提交 checkout 出来跑不过（测试 import 不到包）。
  用 `git reset --soft HEAD~1` 重做成一个自洽提交。
  **判据：任何单次 checkout 出来，测试套件都必须能跑。**
- **中文提交信息用 `git commit -F .git/COMMIT_MSG_TMP.txt`**，别用 `-m "..."`
  （消息里的引号会打断 shell 引用）。
- 文档一致性门禁会因**加测试**而红（要等于 `pytest --collect-only` 真实数），
  改完测试记得同步 README / PITCH / docs/handoff.md。

### R5.1 的前置条件（**不改数据模型就测不了**）

R5.1 的核心指标是「**被后续引用的字段集 vs 从未被引用的字段集**」，但当前
runner **只记 `payload_chars`、不记返回内容**，且工具返回是散文式文本——
**没有"字段"这个粒度**。所以 R5.1 的第一件事是改数据模型（结构化返回 + 字段级
字符数 + **可判定"是否被引用"的最小信息**：值指纹而非全文，PII 与体积都不允许）。
**不写下来，下一阶段就会拿 payload_chars 硬编一个"字段利用率"，那是指标造假。**
