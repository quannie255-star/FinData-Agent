### 本轮最有价值的三个发现

1. **实测替换算**：工具定义的 token 成本**不要用字符数除系数估**——
   同一条 payload 发两次、只切换有没有 `tools`，读上游 `usage.prompt_tokens` 求差。
   实测（7B）：无工具 45 / 4 工具 613 / 27 工具 **2277**；4→27 多花 **1664 token/次**
   （边际 72.3/工具）。**自检**：同 payload 连发 3 次，prompt_tokens 逐次完全相等。
   同时**主动拆掉自己的虚高陷阱**：「占 92.7%/98%」是短 prompt 的产物（探测器其余
   部分只有 45 token），**绝对增量才可迁移**，占比必须同时给分母。
2. **`model mismatch` 的代价是双向的**：同 harness / 同任务 / 同工具清单，
   3B 命中 **0/6**、7B **4/6**，而 3B **prompt_tokens 更高**（30,548 > 28,516，
   多跑一轮多调一次工具）。**换小模型既贵又不准。** 失败原因是具体行为：
   把 `prefix` 传成 `{'path: ': ...}`（**值对、键名错**），独立复现 TSCG 结论。
   处置顺序很重要：**先把自己的错误信息改成可行动的，再去看模型能不能自修**
   ——反过来就是拿模型的锅盖自己的 bug。
3. **`reset_for_test()` 声明与实现不符**（既有缺陷，本轮撞出来）：OTel 的
   TracerProvider 是**进程级单例**，`set_tracer_provider` 第二次被忽略 →
   清缓存后新建的 provider 不生效，span 仍导进**旧** exporter，而
   `get_in_memory_exporter()` 返回**新** exporter → 测试**看起来在验证，其实
   什么都没验证**（当时表现是一个 IndexError，真凶是不一致）。
   **通用教训：「静默不验证」只能靠身份断言抓，数值断言抓不到。**

### 本机环境坑（新增，值得跨会话复用）

- **系统代理拦 localhost**：`curl http://localhost:11434/api/tags` 返回 **502**
  是**代理**报的错，不是 Ollama 报的错。httpx 必须 **`trust_env=False`**。
  Bash 里探活加 `--noproxy '*'`（这样拿到的 000 才是"服务真没起"）。
- **`uv run python` 看到的 `/tmp` 不是 Git Bash 的 `/tmp`**：Bash 里 `> /tmp/x.txt`
  落在 `C:\Users\10393\AppData\Local\Temp\x.txt`，但 Python 里 `Path('/tmp/x')`
  会去找 `C:\tmp\x`。**从 Bash 传路径给 Python 要用 Windows 原生绝对路径。**
- **Bash 里连 `grep` / `head` / `tail` / `sed` 都没有**（WorkBuddy shim 覆盖 PATH）：
  统计行数用 `uv run python -c` 代替，读文件用 Read 工具。
- **`ruff format --check` 不是门禁**：本仓库 75 个既有文件都会被重排，CI 只跑
  **`uv run ruff check .`**（`pyproject.toml` 无 `[tool.ruff.format]`）。别顺手格式化。

## Jev 爆火事件（用户提问触发）：用得上，而且有一条是「别自己造」

**Jev** = TypeSafe AI 2026-09-15 发布的 **System One 决策模型**（闭源、云端 API、无权重）。
不生成文本，只答三种**带类型**的问题：`Choice`（≤255 选项）/ `Score`（有序打分）/
`Noul`（Bernoulli 真假概率），并行评估返回**校准过的概率**。定位「ChatGPT 给人写答案，
**Jev 给程序做判断**」；命名取自**杰文斯悖论**。

**必须打折的（第三方审计 `SamuelSacco/jev-exploration`）**：官方称快 20–400×，
独立实测 **5–25×**；海外延迟实测 **1.6–3.7s**（不是 70–500ms）；准确率**与中档模型持平**；
「不会幻觉」**不成立**（官方文档自己写：类型化输出保证**接口**不保证**真相**）；
**概率校准无公开曲线 = 没法验证**——而校准恰恰是能用它做分流的前提。

### 竞争信号（这条最重要）：`fast-jev-compaction` 离我的命题很近

`tamaratran/fast-jev-compaction`（约 3 天前建仓）自称「用 Jev 决策**替换 Claude Code 的
compaction 摘要**：每个工具调用与结果被打分，过期的丢弃或截断，保留的逐字节不变」。

我读了它的 How it works。**关键一条：送给 Jev 的 state 里，每个工具结果被替换成一行
提示（`ok, 4213 chars (omitted)`）—— 即 Jev 看不到工具返回的内容。**
它只按 goal + 调用输入 + 对话文本问两个 `Noul`：「这个调用该留吗」「这个结果该逐字留吗」，
按 `keepThreshold=0.5` 分三档：都留 / **留调用+结果截断到 300 字符** / 都删。

→ **它仍然是"预置型判断"，只是把规则换成了极快模型；判断依据是合理性，不是证据。**
我的缝隙（证据来自 **trace 里真实发生的引用**）**还在**。§9.5 那条判断因此**成立**，
但要收窄一句话：**「证据不足→可逆处置」不是我的差异化，是共识做法**（它自己也这么做）；
我只剩两样，且都必须靠实测站住：**①证据来自 trace；②有配对验证闭环**。
**风险**：它有分发渠道 + 决策模型，真有价值的话他们两周内能补上这一层——
所以**稀缺的不是"裁剪的点子"，是"能证明裁剪没伤结果的验证闭环"**。

### 落地决定

1. **不自己实现「模型路由」那一臂**——Jev 已是事实标准（LangChain `TypeSafeClassifier`、
   Vercel AI SDK 7 `evaluate`、`eve` 的 auto model selection 默认评估器）。
   R5.2 原设计「字段裁剪 vs 模型路由」**作废**（两者不同层，比不出东西）。
2. **换成同层对手**：「合理性判断裁剪」（Jev 式，结果省略后再问）vs
   「trace 反推裁剪」（我的）——同任务、同质量尺、配对重放。
   若用模型复刻它的协议，只能写「**协议仿真，不是 Jev 本体**」。
3. **不用它做我的第二层语义判据**（`attribution.py` 明确拒绝语义匹配的那一层），
   除非先在自标注集上量出**校准曲线**并写进产物。
4. **不把付费闭源 API 接进 CI**（要 key、无权重 → 门禁里埋外部依赖）。
5. **不因它爆火改主线**：它降低的是**判断单价**；按杰文斯悖论，判断单价降 →
   判断总调用量涨 → 对"内容该不该进上下文"这类高频准入决策是**顺风**。

已写入 `docs/competitive-landscape.md` §10 + `docs/ROADMAP.md` R5.2（改设计）。

## R5.0 全量两臂跑完：**这是目前最强的单个结果**

32 任务 × 2 臂，唯一变量 = 工具清单长度（27 vs 4），模型 `qwen2.5:latest`。

| | `all7b`（27 工具） | `active7b`（4 工具） |
| --- | --- | --- |
| prompt_tokens 合计 | **223,423** | **104,079** |
| 平均每轮 prompt | 2,659.8 | 1,224.5 |
| 关键词命中 | 7/32 | **13/32** |
| 非 ok 结果码 | 28/54 (51.9%) | 22/55 (40.0%) |
| 沉默工具被调用 | **0**（从头到尾） | — |

**三组数字（R5.2 要的那三组，在"定义侧"这条杠杆上已齐）**：
1. **token 降 53.4%**。配对差分 正差 30 / 负差 2 / 相等 0，均值 +3,729.5，
   **符号检验 p = 2.46e-07**。
2. **成本降 ≈ 53.4%**（同模型同单价 ⇒ 比例=token 比例）；按示例单价 $2.50/M
   折算省 $0.2984 / 32 任务（**只算 input，单价须核实**）。
3. **成功率不降反升**：7/32 → 13/32，**McNemar p = 0.03125**，
   6 个不一致对**全部**朝短清单方向（仅 A 命中 = 0）。

**敏感性检验（照 v3.0 前提敏感度实验的做法）**：两臂各 1 次超时，且**不在同一个
任务上**（A 侧 t08 / B 侧 t27）→ 三个口径都算了一遍：
全 32 对 p=2.46e-07 / 降 53.4%；剔 t08 → 53.8%；**剔两侧 → 52.0%、p=8.68e-07**。
**结论不依赖那两个超时。** 反例留档：**2/32** 个任务上短清单更贵（都是关于本项目
自己新代码的任务）→ **"短清单一定更省"是错的**，只有配对分布上成立。

**交叉验证**：§2.1 用受控探针直接实测的工具定义 token 差 = **1,664/次**；
端到端两臂平均每轮 prompt 差 = **1,435.3/次**（1,435/1,664 ≈ 86%，残差来自
轮数构成/返回长度/命中数不同）。**两条独立测量路径互相印证**——工具定义确实在吃
prompt。但**不能写成恒等式**：端到端差分本来就不该等于受控探针差值。

**工具定义占 prompt 的比例：83.9%（27 工具）/ 46.4%（4 工具）——分母是本批短任务
的平均 prompt（2.7k / 1.2k token）**。换成长对话会大幅下降；可迁移的是**绝对量**
（27 个定义每轮固定吃 2,232 token，其中 23 个一次没被调用）。

**新发现（与预期不同）：一半工具调用没落好**（非 ok 结果码 51.9%，`get_signature`
65% 是 not_found = 模型在猜不存在的路径）。**但它不能叫"失败率"**——`not_found`
对搜索类调用可能是正常结果。它是**独立于"定义太长"的另一个浪费来源**，两者不许
合并成一个数字。

**边界**：这条杠杆是**定义侧**，比 R5.2 原定目标（**返回内容**裁剪）容易得多。
它证明的是**方法闭环可行**（测量→裁剪→同批任务重放→三组数字），
**不是**"最难的裁剪问题已解决"。23 个沉默工具是构造的 → **幅度不能当行业事实**。
