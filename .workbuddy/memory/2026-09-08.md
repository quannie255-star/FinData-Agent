## M11：接真实交易日历与公司事件（真实数据 84 分 → 92 分）

接昨天发现的边界，把两个"只有 schema 没有数据源"的洞补上。

**交易日历（核心收益）**
- `tool_trade_date_hist_sina` → 8797 天（1990-12-19 ~ 2026-12-31），落 `trading_calendar` 表
- `TradingCalendar.from_trading_days()` 新增**查表模式**：`is_trading_day` 不再靠
  "周末 + 硬编码节假日"推断，直接查全集。`is_exchange_calendar` 属性区分两种模式
- `with_observed` 在查表模式下并入全集（补接口漏采的零星日子）
- `prev/next_trading_day` 加 `_MAX_LOOKBACK=366` 上限 —— 真实日历有覆盖范围，
  查询超出范围时原实现会**向后无限循环**
- `inspect.Snapshot.from_duckdb` 优先读 `trading_calendar` 表

**为什么必须查表而不能推断**：春节是**全市场同时休市**，那些日子在 stock_daily 里
**没有任何观测**，所以 `with_observed`（"数据里出现过就是交易日"）永远推不出来。
这是硬编码节假日表覆盖不到的根本原因，换多少年节假日数据都没用。

效果：信号 57 → 3、告警 4 → 2（3 条春节误报全消）、健康分 84 → 92。
剩下 2 条核查后是真信号：600030 缺 6 个交易日，同窗口 600519/000858 有 6 天数据
= 个别缺失而非集体休市，"回补漏采"判定成立。

**公司事件**
- `stock_history_dividend_detail(symbol, indicator="分红")` → 除权除息日，553 条覆盖 24 只
  （1995–2026）。这才是 corporate_event 第一个真实的**历史**数据源
- `stock_zh_a_stop_em` → 当日停牌快照（304 只，无历史起止日）。语义是"此刻谁停着"，
  对历史回溯帮助有限，且本次调用网络失败；代码里 try/except + warning 兜住
- `ingest_all(with_events=True)`，默认关（按标的逐个调接口，比日线慢一个量级）

**抑制率仍是 0**：553 条事件一条都没落在告警窗口内，所以真实数据上归因层的
抑制能力**尚未被触发**。合成语料的 100% 精确率是设计出来的对照 —— 这句必须
在 README 里说清楚，否则就是误导。

## 试过但撤回：成交量漂移归因

想加"放量 + 价格同向变动 → 市场放量，降级 P2"，区分评测注入的"单位变更 20x"。
**失败，撤回**：
- 探针算的是 `10日均量 / 前30日均量`，把注入的 20x **稀释成 5.14x**
- 真实政策行情的放量是 **5.40x** —— 两者数值上几乎重合，倍数阈值无效
- 价格判据同样无效：合成语料收盘价本就是随机漫步，10 日涨跌 10% 很常见
- 硬塞规则 → 根因准确率 100% → 85.7%，评测门禁挂（test_eval + test_mcp 两条）

**决策原则**：为修真实数据上的一条告警去牺牲评测门禁是负收益。撤回代码，
把失败的判据和数值写进 README 的"已知局限"。这比假装修好强。

## 顺手修的小 bug

`inspect.py` 的 `_EMPTY_EVENT = ("symbol","event_date","event_type","payload")`
与 db schema 的 `(symbol,date,kind,end_date,detail)` **列名不一致**。
只在"表不存在"的降级路径触发，而 triage 有 `"kind" not in columns` 保护会
直接返回 False —— 等于**静默跳过所有抑制**而不报错。已对齐列名。

- **仓库元信息**：补了 description 与 10 个 topics（之前是空的，面试官点进
  仓库第一眼什么都没有）。走 API PATCH/PUT，用 `git credential fill` 取 PAT
- **README 新增「技术选型：为什么没用这些」**：JD 高频要求 LangGraph / RAG+
  向量库，项目都没用。与其藏着不如讲取舍：
  - LangGraph：核心流水线是确定性 DAG（探针→归因→路由→渲染），无运行时分支
    与回环；套图是把确定的变不确定。真正需要图编排的是"查询时可信"那种有
    回环的对话状态机
  - RAG：归因要精确业务事实不是相似文档；且相似度会返回"看起来像"的事实，
    **一个像的事实比没有事实更危险**（会理直气壮地抑制掉真告警）
  - DuckDB：零运维 + clone 的人第一条命令就能跑出完整结果
- **版本 0.5.0 → 0.6.0 并打 tag**：发现 `ghcr.io/...:latest` 里的镜像是 M11
  **之前**的代码 —— v0.5.0 在 M11 前打的，别人 pull 到的是旧版。M11 是实质性
  功能变更，必须重打。**教训：功能变更后要检查 latest 镜像是否含新代码**
