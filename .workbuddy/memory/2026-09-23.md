## 同日下午追加：新增 `docs/interview-story.md`

用户接着问「**你作为面试官希望面前是一个怎样的项目 / 亮点 / 故事 / 我怎么开发的 / 我的业务思考与权衡**」。
⇒ 交付 `docs/interview-story.md`。结构按**面试官的固定评判顺序**写，因为顺序本身就是评分标准：

1. 你解决的是谁的什么问题（一句话，无形容词）
2. 你怎么知道它有效（基线 / 单位 / 实测还是估的）
3. **你怎么知道你没骗自己（有没有自己推翻过自己）← 分水岭，多数人交白卷**
4. 你放弃了什么、为什么（理由不许是"没时间"）
5. 给 10 倍资源你做什么（知不知道天花板在哪）

配套写了三样：**反面清单**（最怕看到的 6 条，含"提升了 40% 但没基线"「技术栈不是项目」）；
**亮点分级**（6 条站得住的 H1–H6 + 4 条"听起来亮但会被一刀捅穿"的说法与改口方式）；
**三个时长的讲法**（30 秒骨架 / 3 分钟四段 / 追问 20 分钟的两个最硬问题与正确答法方向）。

三条判断，值得留在记忆里：

- **最强的资产是"自己发现并推翻了什么"**，因为**它无法伪造**——敢展示说明有真实测量过程，
  否则根本发现不了自己错了。文档里把 5 次自我推翻做成了表（探针删除 / 第五档处置 / patch 错函数 /
  漏 `--model` / 语料泄漏），每次配"固化成的规则"。
- **"不做清单"比"功能清单"更能说明水平**；但**必须主动说**，被抓出来就把所有数字的可信度拉低了。
- **每一条结论要同时含四样**：数字 / 口径 / 效力 / **不能推出什么**。
  例：「head 裁剪省 23–25% token；7B 代码一致子集上 `exact_hit` k=7 有分辨力且 p=1 ⇒ 没测到伤害；
  **不能说证明无害**；3B 上 k=4 测不出。」

结论：这两份文档构成一对——`product-goals.md` 管**做什么**，`interview-story.md` 管**怎么被检验**。
