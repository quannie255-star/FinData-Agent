## LLM 解析层（同日，Ollama 待用户启动）

`src/findata/chatbi/parser.py`：LLM 只做**填槽**（symbol/intent/日期），
**不写 SQL、不判可信**。理由：本项目卖的是「数字能不能引用」，这个判断
必须可复现可审计，交给概率模型等于用不可信手段证明可信。比 WrenAI/
Databao 的「让 LLM 生成 SQL」更窄，但窄得有理由。

三重不信任（任一失败降级规则解析，沿用 RL 白名单校验与 triage 降级传统）：
symbol 必须 6 位且在股票池 / intent 必须三个之一 / 日期缺年份不猜。
降级原因写进 `ParseOutcome.error`，成本（字符往返）写进 `usage_chars`。

`tests/test_chatbi.py` 15 例（解析 5 + LLM 路径 5 + 门禁两侧 4 + 端到端 1）。
LLM 用例用 `MockLLMClient` 确定性桩，钉的是「模型说错了系统会怎么办」：
幻觉 symbol、非 JSON、非法 intent、服务不可用，四条全部正确降级。

   讲不清比不做更危险）；

   fork 会让面试官记住"他改了 WrenAI"而不是"他发现了可信空白"。

## ChatBI 解析层评测（接 Ollama 实跑，v2.2.0 之后）

Ollama 其实早就装了（0.16.3），此前 `ollama list` 为空只是**服务没起**。
`ollama serve` 后台起后可见 qwen2.5:latest(7B)/llama3.1；另拉了 qwen2.5:3b(1.9GB)。
Ollama 走 OpenAI 兼容端点 `http://localhost:11434/v1`，api_key 填占位串即可。

新增 `scripts/run_parser_eval.py` + `eval/golden/parser_variants.yaml`。

**方法论要点（可复用）**：拿脚本模板生成的题集比「规则 vs LLM」= 自己送分，
必须补一组**基线会错**的题才叫评测。variant 组 6 题专挑规则盲区：intent 同义
表述（「表现如何」「单日成交均值」不在词表）、中文数字日期、量词「号」非「日」；
另留 2 道哨兵确认 LLM 没把对的改错。

**口径**：slot 匹配 / 模型独立答对（未降级且全对，不能把规则兜底算成模型能力）
/ 降级次数 / 字符成本 / badge 下游徽章与 golden 一致（决定性指标）。

**实测**（17 main + 6 variant）：main 组规则与 LLM 均 100%（LLM 降级 4–6 次，
全是「只有年月」的题——模型不会把月份展开成整月区间，是项目约定不是常识）；
variant 组规则 2/6 vs LLM 5/6 → **长尾问法上 LLM 确实赢**。3B 与 7B 最终
准确率打平，7B 只少降级 2 次 → 兜底的是护栏，不是更大的模型。

**顺手修的两个真 bug**（都是解析层从未被真实问句测过才活下来的）：
1. `parse_with_llm` 照单全收 `symbol:null` 和半截槽位 → 加两道降级；
2. `engine.answer` 拼 SQL 前不校验完整性 → 规则解析遇「9 月 4 号」退化成整月
   区间、`as_of=None` 拼出 `DATE 'None'`，报 duckdb ConversionException。
   现改为在入口拦住并给可行动报错。

测试 368 全过（+2），ruff clean。demo 默认模型改 qwen2.5:3b。
