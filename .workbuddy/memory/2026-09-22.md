## github.com 又被代理挡住 → 改用 Git Data API 推送（**SHA 一致，没分叉**）

用户要求"重新推到 github"。实测：`git ls-remote origin master` 报
`CONNECT tunnel failed, response 502`，而 `api.github.com` 返回 **200** ——
与 2026-09-20 那次是同一个形态（git 的 https 传输层走 github.com，被透明代理挡）。

**处置：不走 `git push`，走 Git Data API。** 现成脚本在
`~/.workbuddy/skills/github-actions-smoke-debug/gh_push_api.py`：

```bash
printf 'protocol=https\nhost=github.com\n\n' | git credential fill \
  | uv run python "<skill>/gh_push_api.py"        # 先 dry-run
  | uv run python "<skill>/gh_push_api.py" --apply
```

- 输出：`2854b95 -> 2854b95 OK`，`ref updated -> 2854b95 OK`
- **关键价值：带 author/committer 原始时间戳重建 commit ⇒ API 生成的 SHA 与本地
  逐字节一致**，不产生分叉，事后不需要 reset。
- 推完记得把远端跟踪引用补上：`git update-ref refs/remotes/origin/master <sha>`
  ——因为 fetch 也走不通，不补的话 `git rev-list --count origin/master..HEAD`
  会一直显示"还有 1 个没推"（**假信号**）。
- 凭据探测别打印：用 `subprocess.run(['git','credential','fill'], timeout=25)`
  只报 `password present: bool` 与长度。**没存凭据时它会转去终端交互并挂住**，
  所以必须带 timeout。

**通用教训**：`origin/master` 是本地的引用，它**不会因为远端被改而自动更新**。
"推成功了吗"必须以**远端回读**（API GET ref 或 `ls-remote`）为准，不能用本地引用判断。

## 补掉一个真缺口：**账单里的代码身份是假的**

`code_commit` 取自**语料根**，而语料根是冻结快照、**真正执行的代码在调用方工作区**
⇒「同批各臂同代码」**没有任何产物能证伪它**，只剩 mtime 这种弱证据（`git checkout` 也改 mtime）。
补法：`corpus.manifest_of()`（口径与语料指纹相同，只换"选哪些文件"）+ 账单里记
`executed_code` / `executed_code_root` / `executed_code_commit|dirty`；
`compare_compaction_arms.py` 会核对并支持 `--require-same-code`。

**处置上的一个决定**：带指纹的重跑**不能覆盖原批次**（否则已被文档引用的数字就不可核对了）
⇒ 用 `-fp` 后缀另跑一批，**两批并存**。副产品：两批之差 = **同一臂两次独立运行的波动下界**
（本实验此前一直缺这个数）。

## 一次差点成的假结论：**我把跨模型比较当成了噪声**（本日第二次自查）

**经过**：我为补"代码指纹"重跑四臂，命令里**漏了 `--model`**，而 runner 的默认模型是
`qwen2.5:3b` ⇒ 那批实际是 **3B**，文件名却写着 `active7b-*-fp`。
我拿它跟旧 7B 批比，看到 `fx` 的 ptok 106,843→83,627、返回字符 134K→64K，
**第一反应是"噪声比效应还大"**，并准备据此宣布 R5.2 的结论不成立。**这个读法是错的。**

**怎么发现的**：不是靠直觉，是靠**按纪律逐一核对两批账单的 `scope.model` /
`tools_list_sha256` / `corpus.sha256`**。账单里 `scope.model` 从头到尾写着 `qwen2.5:3b`
——**产物是诚实的，是标签在说谎**。

**顺手得到的东西（意外收获，而且很值）**：
1. 这批误操作**成了合法的 3B 同构重放**，且**首次带上代码指纹**（四臂都是 `ef9f3bca…`）。
   3B 读数：`fx` 83,627 / `ch` 64,074 / `ci` 65,650 / `cp` 62,639 ptok；
   `exact_hit` 6 / 2 / **0** / 3。
2. **跨两个模型的合并读法**（这才敢对外说）：
   - `ci`（裁到 92–96%）**两个模型上都显著变差**（两次 p=0.03125）⇒ **唯一稳的结论**；
   - `ch`（裁到 74–89%）：7B 没测到伤害、3B 方向不利（6/32→2/32，4:0，k=4 未达显著）
     ⇒ **"裁到 88.7% 不掉质量"这句话我主动撤回，改写成「未证实」**；
   - `cp` **两次都测不出** ⇒ **"两次测不出"不等于"两次都没事"**。
3. 副产品：**合法的 7B vs 3B 对比**（4 工具臂、无裁剪）——3B token **−21.7%**、
   `exact_hit` 6/32 vs 7/32（k=5 测不出）。**与 R5.0 的 27 工具臂方向相反**（那里 3B 更贵）
   ⇒ 机制假设"3B 的 token 优势依赖工具清单是否臃肿"，**未检验**。

**固化的三条**：
1. 产物改名 `active3b-*-fp`；**臂名是标签不是证据**，断言只来自账单字段。
2. `compare_compaction_arms.py` 新增"模型"列 + 「这不是对照实验，是跨模型比较」硬警告；
   闸门 `--require-same-code` → **`--require-same-setup`**（代码/模型/语料/工具清单）。
   实测拦住了：`--base active7b-fx --arms active3b-fx-fp --require-same-setup` 退出码 **3**。
3. 这已是**同一类错误的第三次**（移动的语料 §3.5、patch 打错函数 §2.4）⇒
   **对照实验的"只有一处不同"必须由产物核对，不能由记忆核对**，列为本项目头号纪律。

**并补掉一个更严重的缺口（写进 §3.11）**：harness **没固定解码**（无 seed、没压 temperature）
⇒ "同一配置再跑一次差多少"**从来没测过**，所以此前所有质量侧数字
**凡小于噪声下界的都只能写「在噪声内」**。新写 `scripts/repeat_run_variance.py`：
先核对 setup（不一致直接非 0 退出）→ 逐任务差（中位/均值/极值/方向计数/符号检验）→
**质量侧"同配置自己翻几个任务"**，并把"小于哪个数就只能写噪声内"直接打印出来。
**顺序定死：先量噪声 → 再固定解码 → 最后把噪声下界写进对照表**，不许颠倒。

### 5. 环境与协作上的三个新坑

  而 `api.github.com` 稳定 200 ⇒ 取数脚本默认顺序改成 **api → raw**，并把"没走成的那条路失败原因"
  也记进产物（决定"离限流还有多远"要看的正是它）。实测第一次 43/47（4 个 **403 rate limit**），重试后 47/47。
