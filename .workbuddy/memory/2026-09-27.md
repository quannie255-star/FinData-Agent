## 顺带挖出的两件事

1. **全项目最有说服力的资产此前完全看不见。** `logs/` 被 gitignore ⇒ 那段"考试→修复→没回退"
   的历史在 GitHub 上一个字都没有。这是本轮最该修的，且最便宜。
   - 给 `.gitignore` 开了**有理由的**例外：`logs/*` + `!logs/daily/`。
     注意必须写 `logs/*` 而不是 `logs/` —— **git 不会进入被整个排除的目录**，那样 `!logs/daily/` 无效。
   - 日志只是 112K / 30 个文件，体量不是问题；`reports/daily/` 仍排除（那才是可重生成的）。
2. **09-15 19:17 调度器首跑崩过，而且只在调度器会话里复现。**
   - `subprocess._readerthread` → `UnicodeDecodeError: 'utf-8' codec can't decode byte 0xb2`
     → `daily_pipeline.py:65` `TypeError: 'NoneType' object is not subscriptable`。
   - 根因：父进程按 UTF-8 读子进程输出，而子进程在调度器给的**非 UTF-8 控制台**里输出 GBK。
   - 修法（代码里已留注释「管线不许因日志崩」）：`text=True, encoding="utf-8", errors="replace"`。
     **宁可乱码，不许崩** —— 无人值守管线的正确取舍。
   - 编码不一致是有机制的：管线自己写 UTF-8，而 `schtasks.log` 是**调度器 wrapper 的 `>>` 重定向**
     写的 GBK。**用 UTF-8 读它会直接报错**（不是损坏）。

关键是要同时说清反面：**它不生产数字，只回答"可不可信、为什么"**（差异化在归因不在检测）；

### 五个目标词的拆解（写进文档时全部带证据）

- **跑过真实数据：已达成，是全项目最强项**（akshare / 25 标的 / 28,652 行 / 10 个运行日 / 前后对照）。
  这条是重构中最容易弄丢的 ⇒ 纪律：**宁可慢，不要让"连续运行 + 前后对照"断掉。**
- **工程成熟：部分。** 硬门槛是 **无 `LICENSE` 且仓库公开**（`private:False`、`license:None`）——
  别人看到也不能合法复用，成本最低、收益最直接。
- **高可用：部分。** 先给对定义 —— 对"每天跑一次的管线 + 一个 CLI"，**不是 99.99% SLA**，是四件事：
  ①不会挂死（`daily_pipeline.py` 子进程**无 timeout**，这是当前唯一"未开始"项）

## 后续：按冻结判据动手（同日深夜）

方向定了之后，只做**符合冻结判据**的改动 —— 即"增加别人能跑起来的概率"的那些。

### 1. `LICENSE`（MIT）

公开仓库原来的 `license:None` ⇒ 别人看到也不能合法复用，是「不是 toy」的**硬门槛**。
补 MIT（署名 2026 聂权，如需 Apache-2.0 或改署名，改一个文件即可）。
`pyproject` 的 `license` 字段**没动**：`requires-python`/构建后端是 `setuptools>=68`，
而 `license = "MIT"` 字符串形式要 setuptools ≥77，本机 docker build 又无法复现（见用户级记忆）
⇒ 宁可不改元数据，也不赌一次会挂在 tag build 上的改动。

### 2. 管线：加超时 + 原子写（`scripts/daily_pipeline.py`）

- `_run_step` 加硬超时（默认 1800s，`FINDATA_STEP_TIMEOUT_SECONDS` 可覆盖）；
  超时**真的 kill 子进程**、返回 **124**（同 GNU timeout，调度器日志里一眼可辨）、
  超时注记写进步骤日志。异常里的 stdout/stderr 过 `_as_text()`：**宁可乱码不许崩**
  （09-15 那次就是解码崩掉把真相盖住了）。
- 步骤日志与日报 md/html 改 `_write_text_atomic`（同目录临时文件 + `os.replace`）：
  按日期命名的报告写一半被中断，第二天重跑之前没人会发现 —— 这是 ②"不毁用户状态"。
- 新增 `tests/test_daily_pipeline.py`（4 例）：**断言 2s 超时真的掐断 60s 睡眠**（<30s 结束）、
  默认超时有限且有界、原子写不留 `.tmp` 残渣且覆盖干净、正常步骤退出码不被兜底成 0。
- 测试数 577 → **581**，同步 README / PITCH / docs/handoff.md / docs/product-goals.md
  （数字门禁 `test_docs_consistency.py` 真跑 collection 比对，改文档不改正言）。
- `[实测]` 改动后真跑一次 `--skip-ingest`：**exit 0 / 6s / 报告归档成功 / 无 `.tmp` 残留**，

### 3. 运行史口径修正（`scripts/summarize_daily_runs.py`）

**这是我今天第二个自己抓到的口径洞，比第一个严重。**

原来按**日志文件**一行，`RE_START.search` 只取首个匹配 ⇒
`20260915.log` 里其实有 **6 次启动**，表上只呈现第 1 次。表里每个数字都没错，
但读者会把「1 行」当成「1 天」。改成 **一行 = 一次运行**（按「每日管线开始」切块），
并把「前 / 后对照」换成**游程编码**（只陈述顺序，不主张因果）：

```
(告警 7 / 抑制 0 / 健康分 72) × 5 → (告警 1 / 抑制 8 / 健康分 96) × 11
共 17 次启动，其中 16 次走到巡检、1 次没有（09-15 19:17:55 那次调度器编码崩溃）
```

⇒ **证据其实比原来报的更强**：不是"1 次 → 9 次"，而是**前 5 次内部完全相同、
后 11 次内部完全相同**。原来那句「10 个运行日 / 其后 9 次」把同一天的多次运行
吃掉了一半证据。已同步 `docs/final-scope.md` 与 `MEMORY.md`。
