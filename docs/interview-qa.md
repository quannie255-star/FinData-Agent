## 开场：三句话

**谁用**：训练 Agent 的算法工程师。他手里有一批 tool-calling 轨迹，准备做 SFT，
但他**不知道哪几条能喂**——没有标签，逐条看又看不过来。

**解决什么决策**：**这条样本喂还是不喂，以及不喂的话该找谁改。**
不是"数据脏不脏"，是"下一步动作是什么"。

**怎么证明有效**：在一份**我完全没参与制作**的公开语料
（`Salesforce/xlam-function-calling-60k`，20000 条 / 31691 次工具调用）上，
给出 354 条判定（1.77%），**每条带证据链、可逐条复核**；并且这 354 条里
**349 条的根因最终落到了数据源（18 个工具 / 18 个参数），不是样本**——
证明这套判定能把"样本的账"和"数据源的账"分开，而不是笼统报个脏率。

一句话：**我不是在测数据脏不脏，我是在给每条样本判该谁背这个锅。**

## 0. 开场三问

### Q1. 一句话说清你在做什么

给 Agent 训练数据做**质检 + 归因 + 处置**：判定每条轨迹能不能喂训练，
不能喂的要说清**根因在哪一方**，并把处置落到正确的一方上。

### Q2. 你和 Great Expectations / 数据质量平台有什么不同

差在**归因**，不在检测。

- GE 类工具："这一列有 6 行缺失" → 事实，但不告诉你该不该修、该找谁。
- 本项目：缺 6 行是**漏采**（要补采）还是**停牌**（合法，别动）？
  两者**形态完全相同、结论相反**。

这不是修辞。真实数据上这一条直接把精确率从 61.5% 拉到 100%
（`docs/reviews/2026-09-15-attribution.md`，口径：真实告警 7/7 全是合法事件）。
**不做归因的检测器，告警精确率可能只有六成**——六成精确率的告警没人看。

### Q3. 这套东西的核心命题

**形态相同、结论相反的事实，必须用领域知识/协议知识区分开。**

本次自查里我又撞上**第三个变体**（前两个见红旗 #2 和"兜底类"）：

| 变体 | 表面形态 | 真实结论 |
| --- | --- | --- |
| 停牌 | "数据缺了 6 行" | 合法缺失，不该修 |
| schema 矛盾（349 条） | "agent 漏填必填参数" | 数据源 schema 写错，样本没错 |
| 兜底类（5 条） | "步骤硬错误" | 我的规则没认出来，**不代表样本坏** |

三次都是同一个动作做错的：**拿一个"我没证据"的判断，去执行了一个有代价的动作。**

## 1. 产品与价值

### Q4. 产品给谁用、替代了他现在的什么工作

训练数据的**入湖门禁**。替代的是"人工抽检几百条然后凭感觉定规则"，
以及"啥都不做直接全喂"。

### Q5. 你的用户为什么不直接用 LLM 判一遍

因为**成本与可复现性**：

- 判定全是**确定性查表**（工具名在不在注册表、参数与 schema 一致否），
  **不调模型**。20000 条 / 31691 次调用跑完**实测 4.7 秒**（含流式解析
  96MB 原始文件），成本 0。
- LLM 判定不可复现：同一批数据两次跑结论会变，而**过滤是一个要做审计的动作**
  （"这 20000 条为什么只剩 19646 条"必须有确定答案）。
- 项目里的 LLM 归因器（`agent/llm_triage.py`）定位是**兜底层**，不是主判据。

### Q6. 产品 ROI 怎么算

单位不是 accuracy，是 **cost per trusted answer** 与 **拦截率**。

- **省下的**：20000 条里 19646 条可自动放行，不用人看；349 条不丢，
  改成 18 个工具的 schema 修复动作。
- **避免的损失**：349 条样本若按第一版丢弃，损失的是**样本量**；
  但更贵的是**方向错的改进建议**——第一版给这 349 条的建议是"换更大的模型 /
  收紧输出格式"，属于朝反方向使劲（详见红旗 #2）。
- **可计量**：拦截率（命中/总量）、**误杀代价**（本该留的被丢掉）、
  **漏杀代价**（本该拦的进了训练集）、单位样本处理耗时。

### Q7. 为什么不做成 SaaS / 平台

因为**做不成**：质检规则必须贴着数据源的协议细节（工具 schema 长什么样、
哪些叫法是合法的），这东西是跟着数据走的，不跟着我走。所以做成
**可嵌入的模块 + 一条命令跑的 CLI**，而不是平台。

## 2. 数据与评测

### Q8. 数据从哪来，多少条，是不是你自己造的

- 来源：`Salesforce/xlam-function-calling-60k`（ModelScope 公开数据集），
  原始文件 96.1 MB，`sha256:4ef5c6f0dc552f22`（前 16 位）。
- 本轮用 **20000 条 / 31691 次工具调用**。
- **零自造样本**。这条是硬约束，理由见红旗 #4。

### Q9. 规则命中 vs 真实错误——你凭什么说命中的是"错"的

**我不说。这是我本轮改掉的一个措辞错误。**

报告第一节从「发现率」改成 **「命中率」**，并显式加注：

> **命中数不等于错误数**

并且"干净"改成"未命中"，加注 **「未命中 ≠ 确认正确」**。

`examples/trust-filter-report.txt` 第八节（诚实说明）原文：

> **「未命中」不等于「确认正确」**：判定全是查表，未命中只说明这条轨迹
> 通过了我能查的那几项。以 xlam 为例我**拿不到执行反馈**，所以「正样本」
> 的准确含义是「没查出缺陷」，不是「业务结果正确」。

**为什么必须这么说**：我拿不到工具的执行反馈（这数据集只有调用，没有返回），
所以"结果正确"这件事**我根本观测不到**。观测不到的事不能写进结论。

### Q10. 无标签数据上，你怎么知道规则判对了

**没有办法在数据内证明。** 我用两条替代手段，并明确它们的边界：

1. **人工抽检（定向，非随机）**：把命中的 354 条里 top 几类逐条打出原始
   schema 去核。**这一步是真做了**，效果极好——349 条误杀就是这么发现的
   （打印 `calculate_electric_field` 的 schema 原文，看见
   `permitivity` 的描述写"default is 8.854e-12"却没有 `default` 字段，
   而 `charge` / `distance` **反而被标了 `default: 8.854e-12`**——
   把真空介电常数标到电荷量上，物理上荒谬）。
2. **两套归因器的 κ 一致性**：`examples/eval-llm-triage-real.txt`，
   规则归因 vs LLM 归因，n=13，根因标签 **κ=+0.7417**，抑制决策
   **κ=+0.6486**。

**第 2 条的边界必须说清**：κ 是**机器 vs 机器**，不是人 vs 机器；
且 n=13 太小。它只能说明"两套独立实现没跑偏"，**不能替代人工一致性**。

**随机抽样的人工一致性（人 vs 机器、算 κ）我没有做**——这是真实缺口，
见 [不自证的部分](#不自证的部分必须主动交代)。

### Q11. 误杀 / 漏杀的代价你算过吗

算过，而且**误杀是本次自查里最贵的一笔**。

| | 误杀（本该留的被丢） | 漏杀（本该拦的进了训练集） |
| --- | --- | --- |
| 本次实测 | **349 条**（已修，一条样本都不用丢了） | 无法测（无标签） |
| 代价 | 样本量 + **改进建议方向反了** | 训练集被污染 |
| 为什么更贵 | 会让人去改**错的地方**（"换模型"），把资源投到无效方向 | 污染是渐进的、不报错的 |

**处置选择的判据（本轮总结出来的）**：不只看"有多可疑"，还看
**"能不能给出一个可执行动作"和"队列长度"**：

- 5 条 → 人工队列**是**队列 → 交人工
- 349 条 → 人工逐条看等于没有队列 → 必须结构性修复（改 schema）

同一条规矩，两个方向都成立。

### Q12. README 写 353 例测试、CI 写 351 例，哪个是真的

**拷问命中。这是真错，已修，并且加了防回归门禁。**

当时的实际情况比 353/351 还乱：README 两处分别是 353 和 351，
PITCH 同时存在 341 / 351 / 353。

**修法分两层**（`tests/test_docs_consistency.py`）：

1. **文档之间**：扫 `README / PITCH / AGENTS / docs/handoff / docs/ROADMAP`，
   断言当前测试数只有一个值。上线即抓出 `PITCH.md:87` 漏网的 351。
2. **文档 vs 事实**：跑 `pytest --collect-only`（**只收集不执行**，
   2 秒，所以不会递归），拿真实用例数，断言文档写的数字等于它。

**为什么第 2 层必须有**：第 1 层只能保证"文档之间不打架"——
**它们可以一起写错**。实测确实如此：354 这个错数字在 6 个位置同时存在，
一直没人发现，因为**没人拿 CI 的数字去比对**。

**顺带查出两个连带问题**：

- `354` 在文档里**同时表示"测试数"和"命中数"两个语义**（两者恰好都是 354）
  → 已全部消歧
- README 的产物清单是**改判前的旧值**（`discard.jsonl 354`），
  与真实产物（349 / 5）不符 → 已回填实值

**现在的规矩**：改完测试如果不更新文档，门禁直接红。本轮它红了 3 次，
每次都逼我去同步——这是它该有的样子。

## 3. 归因核心

### Q13. 你的归因规则具体是什么，是不是一堆 if-else

是确定性规则（**刻意的**，理由见 Q5）。但分层，不是一坨 if：

- **探针层**（`agentops/probes.py`，**只观测不判断**）：
  5 类形态信号——`degrade` / `abort` / `retry_storm` / `ungrounded_slot` /
  `silent_mismatch`。
- **归因层**（`agentops/triage.py`，**判断全在这里**）：
  把形态信号映射到根因类别 → 再到处置档位。

**为什么探测与判断必须分离**：判断层可以**整体替换成 LLM** 而不动探针。
这是给未来留的接口，不是为了分层而分层。

### Q14. 规模型幻觉工具名你查吗

查，但**这一项在本次数据上 0 命中，等于没被验证到**。

样本里的所有调用都落在给定工具列表内（`tool_missing` 0 命中）。
所以我在报告里主动写了：

> 「工具不存在」这一项 0 命中……**这一项没被验证到**，
> 不能说它能查幻觉工具名。

**0 命中的类别不能号称"支持"**——0 命中可能是规则对，也可能是数据里根本没有
这类脏。我分不出来，所以我说分不出来。

### Q15. LLM 归因和规则归因，谁说了算

规则是主判据（可复现、零成本），LLM 是兜底层 + 对照组。
一致性 κ=+0.7417（n=13，见 Q10 的边界说明）。

## 4. 工程与训练集成

### Q16. 产物长什么样，能不能直接喂

**能，形状就是 OpenAI `messages` + `tool_calls`，落盘即训练，中间不写转换层。**

```
data/filtered/
  train.jsonl               19646  ✓ 正样本
  schema_defects.jsonl        349  🔧 待修 schema
  review.jsonl                  5  ⚠️ 需人工
  discard.jsonl                 0  ✗ 丢弃
  not_failure.jsonl             0  ⊘ 不算失败
  tool_schema_defects.json        工具级待修清单（18 个工具 / 18 个参数）
  manifest.json                   计数 + 口径 + 可复现三元组
```

**一个容易错的细节**：`arguments` 在 OpenAI 协议里是 **JSON 字符串**不是对象。
这个细节错了，下游加载会**整批失败**。

### Q17. 为什么不合并成一个带标签的大文件

**因为那等于把我卖的东西推给下游。**

下游训练脚本通常"一个目录一个意图"。合并成一个文件再靠 `findata.verdict`
字段过滤，等于要求下游**自己判断哪些该喂**——而那正是本产品的核心价值。
分开写，下游 `train.jsonl` 直接吃。

### Q18. 训练元数据剥离——判定结论会不会污染训练

**不会进训练**，但**目前也没自动剥离**，这一点要说清。

实测 `train.jsonl` 的一行：

- top-level keys：`findata / id / messages / row / source / tools`
- `findata`（判定结论：处置/根因/证据/建议）是**兄弟键，不在 `messages` 里**
- 实测断言：`findata` 不出现在任何 message 中（`False`）

所以标准训练加载器只读 `messages` → **结论进不了模型输入**，物理上污染不了。

**但风险是真实的**：不剥等于依赖"下游会正确地只读 `messages`"。
下游若用 "拼接所有字段" 的土办法，判定文本就会进 prompt。
**正确做法**（未做）：落盘时把训练字段与血缘字段分开成两个文件，
训练文件只留 `messages`，血缘留 `*.meta.jsonl` 按 `id` 关联。

### Q19. 判定结论为什么挂在样本上，不单独存一张表

因为**分开存会漂移**：改一行代码忘了同步，样本和结论就对不上号，
而这种错**在训练跑完之前不会有任何报错**。

挂在一起，下游拿到样本就知道为什么留/为什么丢，不用回头查报告。
（副作用就是 Q18 里说的：需要显式剥离。）

### Q20. 沙箱

**进程级，不是容器级——这是我明确知道并主动交代的短板。**

- 能做的：超时（主动触发）、输出截断、信号捕获
  （`examples/sandbox-signals.txt`）
- 做不到的：
  - **内存限制只在 Unix 生效**（`resource.setrlimit`）。Windows 没有这个
    系统调用，代码**明确标 `memory_limit_applied=False`，不静默降级**。
  - gRPC 的 `deadline exceeded` **仍识别不了**（关键词表对不上）。

### Q21. 规则更新后，旧的过滤结果怎么复现

**光有代码 commit 不够。** `manifest.json` 里落**可复现三元组**：

```json
"reproducibility": {
  "code_commit": "3f99b7bd...",
  "rules_version": "2026-09-18.2",
  "data": { "path": "data/raw/xlam/...json",
            "sha256_16": "4ef5c6f0dc552f22", "bytes": 96116570 }
}
```

- `rules_version`（`triage.RULES_VERSION`）：**改判定逻辑必须动这个号**。
  只记 commit 不够——规则常量可能改了**没提交**，落盘样本照样与代码对不上号。
- `data` 指纹：**公开数据集会被作者修订**，本地缓存也会被重新下载覆盖。
  同一套规则跑在两版数据上结果不一样，没有数据指纹就查不出为什么。

缺任何一项，"这批样本是怎么筛出来的"就复现不了。

### Q22. 百万级怎么办

**结构上已经成立，但没有实测**（这点要诚实）。

内存与语料规模无关，逐条核过：

- 入：`ijson` 流式读，**不整份 load**。96MB 全 `json.load` 会把开发环境撑爆
  （本机实测连 echo 都打不出来）。
- 出：`SplitWriter` **流式写**，一条一行边生成边落盘，打开的是 5 个文件句柄
  不是 5 个内存缓冲。
- 状态：计数器按类别数有界；`ToolDefectTally` 按 (工具,参数) 对数有界；
  样例列表硬截断在 8 条；探针状态是**每条轨迹内部的**（逐条核过
  `to_trace`，无跨记录累积）。

所以 **20000 条和 200 万条的内存占用一样**。

**没做但要做**：① 多进程分片（`--shard i/n`）把 4 秒线性摊开；
② 落盘按 hash 分桶避免下游单文件过大；③ 百万级下 `ToolDefectTally`
需要 shard-merge。**这三条是设计，不是已实现。**

### Q23. 测试与 CI

- **358 例测试**（`uv run pytest`），ruff line-length 100 全绿。
- CI 三关 + `ci-gate` 聚合；**文档一致性门禁也在里面**（Q12）。
- **门禁有没有用，看它抓到了什么**：本轮三处真错都是门禁抓的
  （PITCH 漏网 351、测试数 354→358 两次漂移、README 旧值）。

## 5. 压力测试：脏数据类型判定表

> 说明：这份拷问列的 8 个具体 case 我没有原文，所以我按**会拿来考我的脏数据
> 类型**列一张判定表，每类明确"能查 / 查不出 / 靠什么查"。
> **"查不出"是答案的一部分**，不是漏答。

| # | 脏数据类型 | 我的行为 | 依据 |
| --- | --- | --- | --- |
| 1 | **工具名幻觉**（调了不存在的工具） | 能查 → `tool_missing` → `⊘ 不算失败`（宿主配置问题，**别当负样本**） | 探针在；但**本批 0 命中，未验证** |
| 2 | **参数名/类型与 schema 不符** | 能查 → `param_error` → `✗ 丢弃` | 与工具 schema 逐字段比对 |
| 3 | **工具 description 承诺默认值但 schema 未标** | 能查 → **`🔧 待修 schema`**（样本留着，改数据源） | 本批 349 条，已修正（红旗 #2） |
| 4 | **同一工具、同参数重复调用** | 能查 → `step_error` → **`⚠️ 需人工`** | 本轮从 `✗ 丢弃` 改判，理由见红旗 #2 的第 3 个变体 |
| 5 | **超时** | 能查（**但只看异常文本**）→ `env_timeout` → `⊘ 不算失败` | ⚠️ **红旗 #3 成立，这是缺点，见下** |
| 6 | **参数值语义错误**（单位错、`"2"` vs `2`、量纲错） | **查不出** | 查表法的天花板：要判值对不对，得知道工具的语义 |
| 7 | **中途放弃**（工具只调了一半、任务没完成） | **查不出** | 没有完成度探针；要判完成度得有执行反馈 |
| 8 | **结果对但路径脏**（走了兜底还蒙对） | 能查 → `lucky_guess` / `degrade_*` → `⚠️ 需人工` | "结果对了、路径脏了，当正样本会教会模型蒙也能过" |
| 9 | **槽位幻觉**（补了用户没给的值）/ **区间口径不符** | 能查 → `hallucinated` / `mismatch` → `✗ 丢弃` | `ungrounded_slot` 探针**不需要 golden 标签**，生产环境也能跑 |

**必须补一句**：#6 / #7 查不出，根因是**同一个**——我只有调用、没有执行结果。
要覆盖它们，得拿到工具返回值（或至少工具签名里的语义约束），
那是数据源侧要补的东西，不是我加规则能解决的。

**另外注意 #9 的处置与 #8 不同**：槽位幻觉是**静默错**（链路没断、
完整性校验也放行），危害大于"路径脏"，所以判丢弃而不是交人工。
严重度分 loud / silent 两档就是这个用途。

## 6. 收尾五问

### Q24. 这个项目最难的地方是什么

**不是写规则，是忍住不用规则干超出它证据范围的事。**

三次做错的根源都是同一个动作：**拿一个"我没证据"的判断，去执行一个有代价的动作**
（丢样本 / 改建议方向 / 报脏率）。

### Q25. 你最大的短板

三条，按严重度排：

1. **无执行反馈** → "正样本"只能叫"没查出缺陷"，**不能叫"业务正确"**。
2. **人工一致性（人 vs 机器 κ）没做**，只有机器 vs 机器的 κ（n=13）。
3. **归因准确率无法在真实数据口径下测**（无标签），R4.1 门禁 ≥90% **保留红灯**。

### Q26. 如果给你两个月，你砍到什么

**只留一条链路**：`真实语料 → 探针 → 归因 → 处置 → 落盘`，
加上一条 CI 门禁。理由：**投递材料只能讲清一条主线**，
多留的每一块都会在面试时把注意力从主线上带走（红旗 #5）。

砍掉的：A 股领域包、通用数据包、MCP / HTTP 接入面、看板、可观测层——
**全部封存不删**（它们是已验收里程碑的证据，PITCH 的数字直接引用其归档）。

**为什么"封存而不是删除"**：删除会连带删掉引用其归档的数字，让 PITCH 失去证据。

### Q27. 你还想做什么

按优先级：

1. **人工抽检的 κ**（补上 Q10 的真实缺口）：分层随机抽 50~100 条，
   人工判 + 机器判，算 κ 与混淆矩阵。**这是目前最该做的一件事**——
   它把"我觉得规则对"变成"规则和人一致到多少"。
2. **超时的多证据归因**（红旗 #3 的修法）：见下。
3. **训练元数据自动剥离**（Q18）：训练字段与血缘字段分开落盘。
4. **执行反馈接入**：只有它能打开 #6 / #7 两类盲区。

### Q28. 这个项目能撑住多久的追问

撑得住**归因与处置**这条线（有真实数据、有归档、有改判记录、
有被抓到的真错）。撑不住**"准确率多少"这个数**——我没法给，给了就是编。

**我宁愿说"这个数我测不出来"，也不报一个 100%。**
这一条我已经在 ROADMAP 里写成硬规矩：

> 留着它当素材：面试时能讲清为什么测不了，**比报一个 100% 可信得多**。

## 五个红旗：逐条正面回应

### 红旗 #1：无标签却把规则命中说成错误率 —— **成立，已改**

原来的写法：报告标题「发现率」，字段「有问题 / 干净」。

改法：

- 「发现率」→ **「命中率」**，加注 **「命中数不等于错误数」**
- 「干净」→ **「未命中」**，加注 **「未命中 ≠ 确认正确」**
- 变量名 `n_bad` → `n_hit`（代码里的措辞也算措辞）
- `manifest.json` 的 `note` 把这两句话写进**产物本身**——
  半年后回头看，不靠人记忆

### 红旗 #2：`schema_contradiction` 可能误杀合理省略参数的样本 —— **成立，已改，这是最严重的一处**

**直接说结论：误杀了 349 条。已修，修正后一条样本都不用丢。**

**取证过程**（不是辩解，是查数据）：

1. 打印 `calculate_electric_field` 的原始 schema：`permitivity` 的描述写着
   "default is 8.854e-12"，但**没有 `default` 字段**；而 `charge` /
   `distance` **反被标了 `default: 8.854e-12`**（把真空介电常数标到电荷量上，
   物理上荒谬）。
2. 全库统计：**58105 个 tool 里，带 `required` 字段的是 0 个**；
   125120 个参数条目里 92884 个（**74%**）带 `default`。
3. → **"缺参数 = 漏填必填项"这个前提是我自己发明的，数据源从未声明过。**
   模型省略一个描述里写着有默认值的参数，是**合理行为**。

**改法：新增第五档处置 `🔧 待修 schema`**——样本留着，去改数据源。

**为什么是第五档而不是"需人工"**：因为**根因在数据源，处置就该作用在数据源上**。
配套 `ToolDefectTally` 把逐条轨迹缺陷聚合成**工具级清单**：

> 18 个工具 / 18 个参数要改（不是 349 条样本要人工看）

**同一份事实，两种表述，一个没用一个有行动。** 349 条逐条人工看等于没有队列；
18 个工具改完重跑，样本全部回来。

**第三个变体（自查时新发现）**：`CAT_STEP_ERROR` 是**兜底类**，定义就是
"归不到上面几类"，也就是"我没认出来"，却被映射成 `✗ 丢弃`。
真实数据上这正好吃掉 A 类全部 5 条——而 `to_trace` 的注释自己写着
"**值得人看一眼**"，处置层却判了丢弃。**探测层与处置层口径打架。**
已改判 `⚠️ 需人工`。

### 红旗 #3：timeout 一律归环境，掩盖 agent 策略缺陷 —— **成立，未修，但说清修法**

**代码现状（如实）**：判定只看异常文本——

```python
if "timeout" in flat or "timedout" in flat or "超时" in flat:
    cat = CAT_ENV_TIMEOUT
```

`flat` 是原文本折叠空白与标点后的结果（这样 `timed out` /
`TimeoutExpired` / `timeout` 能归一处），**但判据仍然只有"是不是超时"这一个信号**。

**这条批评是对的**：超时也可能是因为 agent 把参数写错导致工具处理了海量数据、
或者陷入无效重试——**这种情况下超时是症状，agent 策略缺陷才是病因**。
一律归环境，就会把这类 agent 缺陷洗白成"环境问题，别当负样本"。

**改进方向（多证据归因，三步）**：

1. **超时前是否有进展**：轨迹在超时前是否产出过有效工具返回。
   无任何返回即超时 → 更可能是环境；有返回后超时 → 更可能是策略（越滚越大）。
2. **调用参数是否离谱**：参数规模与同工具其他调用的分位数比
   （如 `limit=10^7` 这种）→ 命中则归 `param_error` 而非环境。
3. **是否已在原地打转**：与 `retry_storm` 交叉——超时 + 同参数重复 ≥2，
   归策略而非环境。

**为什么现在没改**：本批数据 `env_timeout` **0 命中**，即这条路径
**没有被真实数据验证过**；在没有正例的情况下改判据，就是上次误杀 349 条
那个错误的翻版（**凭想象设口径**）。正确顺序是：先拿到带超时的真实轨迹，
再按上面三步加判据。

**这条我明确记在 `docs/jd-coverage.md` 的"洞"清单里**：

> 关键词归因在 held-out 上 `env_timeout` 0/20——**这条是真没验证过**

### 红旗 #4：held-out 63.6% 但门禁 ≥0.9，泛化没被真正考核 —— **成立，且我刻意不划掉**

**事实**：R4.1 的门禁写着"归因准确率 ≥90%"，**至今未打勾**。
早先用自造合成集测出 100%，换成从未参与调参的 held-out 集掉到 **63.6%**

**并且我把这个红灯写成了面试素材**：

这两件事我从来不混着说。

### 红旗 #5：主线、旧模块、MCP、A 股、通用包全堆在一起，产品定位漂移 —— **成立，这是最该被问的一条**
