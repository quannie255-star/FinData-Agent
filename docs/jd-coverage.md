## 4. 建议：补「Agent 轨迹的可信与归因」

### 为什么是这一段

1. **和现有归因引擎是同一块肌肉。** findata 现在的本事是"从形态推断根因，
   区分形态相同但结论相反的两个原因"（停牌 vs 上游停更）。Agent 失败归因
   是同一个问题：`tool 参数写错` vs `tool 根本不存在` vs `沙箱超时`，
   日志形态几乎一样，结论完全相反。
2. **一次性命中 JD9 几乎全部条目**（数据合成、沙箱、评测管线工程化、
   评测归因分析、Tool Calling、MCP、Vibe Coding），外加 JD8 的 MCP 与
   自进化、JD1 的 JSONL/tool_calls 数据结构、JD3 的自动化评测。
3. **自带真实数据源，不用造假。** findata 自己的 ChatBI 就是个 Agent：
   23 道题 × 2 种解析器 = 46 条真实轨迹，其中 5–7 条含**降级事件**——
   那就是天然的 tool-calling 失败样本。这比造合成数据硬得多，也"真实可用"。
4. **C 类 JD 数量最多（5/10）、最新、竞争最少。**

## 5. 明确不补的东西（以及为什么）

| 不补 | 理由 |
| --- | --- |
| Spark / Flink / Hive | 单机项目硬补 = 玩具，面试一问"你们集群多大"就穿。补了反而暴露短板 |
| RAG / 向量检索 | JD 里出现 2 次，但 findata 用不上。硬塞会毁掉"探测与判断分离"铁律——**这条我之前就否决过，不因为 JD 出现就改口** |
| A/B 实验 / 统计建模 | B 类赛道的核心，但那是另一个项目。与其两头都要，不如 C 类打透 |
| 前端全栈 | JD8/10 要，但全栈是另一个项目的工作量，会稀释主线 |

**代价：放弃 B 类（JD 2、4）**。这两个岗位建议靠 SQL/Python 基本功 + 别的项目/课程经历去凑，findata 不负责覆盖它们。
