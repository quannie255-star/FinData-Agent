## 开场：你要的三句话

> 你要求：别从架构图开始讲，先用三句话回答——**谁用、解决什么决策、
> 怎么证明有效**。

**谁用**：训练数据工程师 / 做 SFT 的算法同学。他要交一批轨迹去训 tool-calling
模型，但他手上没有"哪条脏"的标签。

**解决什么决策**：**这条样本进 train 还是不进，以及不进的那些该找谁改**。
不是"数据健不健康"这种报告式问题，是一个逐条的放行/拦截决策，而且要能说清
责任方——是 agent 的错（该换模型），还是工具 schema 的错（该改数据源）。

**怎么证明有效**：三条，都能被现场复核：

1. **一条命令跑全量真实语料**（`scripts/run_trust_filter.py`，6 万条 / 16 秒，
   无一条样本是我造的），产出 `examples/trust-filter-report.txt`；
2. **同一份数字进 CI**：判定逻辑的行为漂移会被 364 例测试 + golden 拦住，
   不是"我本地跑过"；
3. **反过来证伪自己**：报告第八节记录了一个被**主动删除**的探针
   （全量命中 2162 条，查完发现是我自己抓错了东西）。一个不会删自己规则的
   系统，它的准确率只可能虚高。

第 3 条是这三条里最重要的。前两条证明"能跑"，第 3 条才证明"在质检而不是在

## 真正的问题：规则脚本 vs 质检系统的四条分界线

你这一轮清单的所有子问题，其实都在问同一件事。我的回答是：**分界线不在
"规则多不多"，在"规则和结论之间有没有一层可问责的判断"**。具体四条，
每条都能在代码里指给你看：

| 分界线 | 规则脚本 | 这个项目 | 证据 |
| --- | --- | --- | --- |
| **1. 观测与处置是否分离** | 命中即处置，一个 issue 对应一个动作 | 同一个观测在不同上下文下结论相反 | `schema_contradiction`（形态=漏填，结论=数据源的错）；`env_timeout`（形态=失败，结论=不算失败） |
| **2. 观测的前提有没有标出处** | 把"我认为的必填"当"数据源声明的必填" | 每个判据都标了是**数据源声明**还是**我自己设的口径** | `xlam.required_params` 的 docstring 明写"该数据集 `required` 字段为 0，这是我设的口径" |
| **3. 结论强度是否与证据强度绑定** | 命中=错误，未命中=干净 | 命中≠错误、未命中≠确认正确、`missing required`≠漏填 | 报告首行、第八节；变量名从 `n_bad` 改成 `n_hit` |
| **4. 能不能删掉自己的规则** | 只会加规则，准确率单调上升 | 有主动删除的记录，且写进产物 | 报告第八节：类型/默认值冲突探针，全量 2162 命中 → **删除** |

第 4 条是我最想被问的。**一个从不删规则的质检系统，它的指标一定是虚高的**
——因为规则集合只会往"能命中"的方向长。这个项目删过一个探针，也改判过一批
结论（349 条从"丢弃"改成"待修 schema"），两次都是往**少报**的方向走。

> 一句话版本：**规则脚本输出"我命中了什么"，质检系统输出"我能证明什么、
> 以及我证明不了什么"。**

## 0. 开场三问（Q1–Q3）

### Q1. ground truth 从哪来

**没有 ground truth，这是设计而不是缺陷。**

- 数据集本身**不带标签**：`Salesforce/xlam-function-calling-60k` 只有
  「query + 工具列表 + 期望调用」，没有"哪条脏"的标注。`glen` 里我刻意只写
  `{source, row, unlabeled: True}`——**往 golden 里塞一个"正确答案"，
  等于把结论写进前提**（这条是 `tests/test_xlam_adapter.py` 钉住的）。
- 我用的 ground truth 是**两种确定性事实**，都不依赖标签：
  1. **数据源自己的声明**（schema 里写的 `default`、description 里写的话）
     ——冲突可以在两个字段之间逐字比对，不需要任何人判断；
  2. **轨迹自身的内部一致性**（同一个工具名、同一份 schema、调用的参数名与
     参数集是否相容）。
- 所以我能给的不是"准确率"，是**"这条判定依据哪两处事实"**。每条判定都带
  `row` 号，可以回到原始 JSON 逐字复核。

**代价我认**：没有标签，我就**测不出规则准确率**（ROADMAP R4.1 那条
「归因准确率 ≥90%」的门禁至今是红灯，是我刻意留的，见红旗 #4）。我选择
"能证明依据"而不是"能报一个准确率数字"。

### Q2. 这 1.77%（现在 2.25%）的命中率，对训练的影响与 ROI

**先说口径**：2.25% 是**命中率不是脏率**。命中 1351 / 60000。

**它值多少，取决于那 1351 条里有多少会真的伤害训练**——这个数我**拿不到**，
因为我没有做模型训练对照（本机 RTX 4060 8GB，跑不出有统计意义的对照；
就算跑了也说不清是过滤的功劳）。**这一格是空的，我不编。**

我能算的是**成本侧**，它不需要标签：

| | 数量 | 人工成本 |
| --- | --- | --- |
| 原始命中（按样本表述） | 1351 条 | 逐条看 = 没有队列 |
| **聚合后（按数据源表述）** | **21 个工具 / 21 个参数** | **21 个改动，一次做完** |

**ROI 的落点在最后一行**：1351 条样本的问题，实际只需要改 21 个 schema 字段。
这是"同一份事实的两种表述，一个没用一个有行动"——而把表述从前者换成后者，
是本项目 90% 的价值所在。

另外，数据集作者自述「约 5% 的样本在验证中发现小错误，整体质量 >95%」
（见 `llmconfigurator` / `innovatiana` 的数据集页）。我的确定性探针命中
2.25%，是那个 5% 的**子集**（我只查参数级一致性，查不了参数值语义错）。
**方向一致，量级一致——但这只说明我没跑偏，不说明我查全了。**

### Q3. 成功指标与代价函数

**成功指标（我能测的）**：

1. **拒答率 / 兜底率**：规则覆盖不到的比例。当前 = 兜底类占命中
   **65 / 1351 = 4.81%**。这是我的"我不知道"的诚实刻度。
2. **误杀率**：本该留的样本被丢的比例。当前 **丢弃 0 条**
   （`discard.jsonl` 0 条）——不是"我很准"，是因为**凡是我没把握的一律不丢**，
   交给人工或交回数据源。
3. **可执行性**：产物是"21 个参数要改"还是"1351 条样本不要了"。

**代价函数（不对称，这是关键）**：

```
丢一条好样本的代价   >>   漏掉一条脏样本的代价
（不可逆：样本没了就是没了）  （可逆：脏样本还在，下一轮还能捞）
```

两者其实都不小，但**可逆性**是决定性的。所以我系统的默认动作不是"丢弃"，
而是**在证据足够时判"数据源的账"，证据不足时交人工**。这条不对称是我所有
阈值选择的依据——**在信息不足时选可逆的那个动作**。

现在按这个代价函数看实际分布：

```
✓ 正样本       58649   97.75%   ← 含义：没查出缺陷（不是"业务结果正确"）
🔧 待修 schema   1286    2.14%  ← 根因在数据源，样本留着
⚠️ 需人工           65    0.11%  ← 我没认出来（不是"样本坏"）
✗ 丢弃               0    0.00%  ← 零误杀
⊘ 不算失败           0    0.00%  ← 环境类，本批没出现
```

**注意 `✗ 丢弃 = 0` 不代表这个系统不会判脏**——它代表我**没有足够的证据去
判一条样本该丢**。把"我没证据"和"我证明它坏"混起来执行，就是这个项目要防的
那类错误。

## 1. 产品与价值（Q4–Q7）

### Q4. 目标用户与不可替代点

**用户**：训练数据工程师 / 做 SFT 的算法同学。

**他现在的替代方案有两个，都不好用**：

| 替代方案 | 它给什么 | 缺什么 |
| --- | --- | --- |
| 人肉抽检 | 少量高可信判定 | 看不过来；且**没有队列概念**（"1351 条" 不是任务，是恐吓） |
| 通用数据质量平台（Great Expectations 等） | 表级/列级断言、空值率、分布漂移 | **没有"该怪谁"**——它只能告诉你数据不符合预期，不能告诉你根因在 agent 还是在 schema |

**不可替代的点只有一句**：我把"这条轨迹脏了"翻译成"**这是谁的账**"。
形态相同的两种事实（必填参数没传 / 工具 schema 自相矛盾），结论完全相反，
处置方向也相反：一个该动模型，一个该动数据源。

这个项目已经攒到**三个变体**，都是同一个动作做错：

1. 缺 6 行数据：**停牌**（合法事实）还是**上游漏采**（事故）
2. 必填参数没传：**agent 漏填**（能力）还是**schema 自相矛盾**（数据源）
3. 规则没认出：**"我没证据"** 还是 **"数据是坏的"**

三个变体的共同形状：**拿一个"我没证据"的判断，去执行一个有代价的动作。**

### Q5. 为什么过滤而不是修复

**这个问题问错了对象——修复是我的默认动作，过滤是最后的兜底。**

代码里的证据（`src/findata/agentops/triage.py` 的 `_VERDICT` 映射）：

| 观测 | 处置 | 为什么 |
| --- | --- | --- |
| `param_error`（agent 真写错参数） | ✗ 丢弃 | 这是模型的账，改数据没用 |
| `schema_contradiction`（数据源自相矛盾） | **🔧 待修 schema** | 根因在数据源，处置必须作用在数据源上 |
| `env_timeout`（环境问题） | **⊘ 不算失败** | 重跑可能就成了，当负样本丢是浪费数据 |
| `step_error`（规则没认出来） | **⚠️ 需人工** | 认不出来 ≠ 样本坏 |
| `hallucinated` / `mismatch` | ✗ 丢弃 | 静默错，危害大于路径脏 |

五档处置里有**三档都不是丢弃**。第一版恰恰相反——它把 1286 条 schema 缺陷
全判成 agent 能力问题并丢弃。**那次改判（`e85dd01`）就是把"过滤"改回"修复"：
产物从"1286 条样本不要了"变成"21 个工具 schema 要改"。**

### Q6. 98.23% 正样本，价值是不是太薄？误杀 1% 净收益可能为负

**分两半答。**

**第一半（价值太薄）：** 这个数（现在 97.75%）是**已清洗过的公开数据集**的
数字，不代表生产环境。我把它写进报告第八节当免责声明，不拿它当成绩。

**但更重要的是：98% 正样本不等于我的工作量只有 2%。** 因为我的产物不是
"筛掉 2%"，是"**定位到 21 个 schema 字段**"。这 21 个改动会让 1286 条样本
回到正样本——**收益是 1286 条样本，不是筛掉 1351 条**。

**第二半（误杀 1% 净收益可能为负）：这半你完全对，而且我按这个方向做了两个
决定。**

1. **丢弃归零**：我没有任何一档处置在"证据不足"时丢弃。当前丢弃 0 条，
   不是因为样本干净，是因为我**没证据**。
2. **可逆优先**：改 schema 可逆（改错了改回来），丢样本不可逆。
   在信息不足时选可逆的那个。

**代价算给你看**：假设我按最粗的口径判——"必填参数没传就丢"，会丢 1286 条
（占 2.14%）。如果这里面有哪怕 1% 是好样本（13 条），我损失的是 13 条**不可
恢复**的训练数据；而收益是"少训 1273 条有缺陷的样本"。**这个交换在算不出
标签的情况下不该做。** 正确解法是改 21 个 schema——**代价是 21 次改动，
收益是零损失**。这就是"修复优先于过滤"的算术。

## 2. 数据与评测（Q8–Q12）

### Q8. `xlam` 是 function calling 数据，不是 Agent 轨迹——平均 1.58 次调用凭什么叫轨迹质检

**这一条你说得对，是产品与数据口径的真实差距，我不辩解。**

先把事实摆准（全量实测）：60000 条记录 / 100011 次调用，**平均 1.67 次**：

```
1 次: 28461   2 次: 25422   3 次: 4697   4 次: 1056   5 次: 187
6 次:   94    7 次:  20     8 次: 12     9 次: 12     ≥10 次: 63
（最长 52 次）
```

**它确实不是 Agent 轨迹**，差在三处：

| Agent 轨迹有的 | `xlam` 有没有 | 后果 |
| --- | --- | --- |
| 多轮 ReAct / 观察-行动循环 | **没有**，一次 query 一次性给出全部调用 | 测不了循环里的策略退化 |
| 环境反馈（工具返回值） | **没有** | 测不了"拿到错结果后能不能恢复" |
| 状态跨轮演化 | **没有** | 测不了上下文污染、状态漂移 |

**所以严格说，我做的是"tool-call 序列质检"，不是"Agent 轨迹质检"。**
我在文档里说"轨迹"是**放宽了口径**，应该改成"工具调用轨迹（tool-call
trace）"。

**为什么还是选它**（不是找借口，是取舍）：我要的是**真实的、无标签的、
别人产的**工具调用数据，因为自造样本证明不了自己的规则。它满足前三条，
缺的是"多轮"。**一个诚实的边界**：我所有关于"循环/恢复/状态"的能力
（`probe_retry_storm` 等）在本批 0 命中，**即这些能力没被真实数据验证过**
（报告第八节已写）。

要有真实多轮轨迹，得自己跑本机模型（`scripts/run_agent_trace.py` 有 48 条
本机 Ollama 真实轨迹），但那又变成"自己产的"——**这是本项目的真实约束，
不是我想绕过的**。

### Q9. 无标签怎么算准确率、人工抽检、kappa、置信区间

**逐项，有做的、有没做的。**

| 项 | 状态 |
| --- | --- |
| 规则准确率 | **测不出**（无标签），ROADMAP R4.1 门禁刻意保留红灯 |

**必然虚高**（我知道规则想抓什么，等于被试和主试是同一个人）。
**一个虚高的人工一致性数字，比没有更糟——它会让人相信一个没被验证的系统。**

**能做但没做、且成本可承受的**：请一个人**不知道规则细节**的人，对**随机
抽 100 条**做三分类（正/脏/说不清），然后算 κ。这个我在 Q33 列为第一优先
要补的事。**我现在没这个数，直接报 0。**

### Q13. 举一条原始 JSON（追问 `required` / `default` / `description` 分别是什么）

**这是全项目最值钱的一条原始记录。** 原文（`Salesforce/xlam-function-calling-60k`，
`row 65`，`tools[0].parameters`，逐字）：

```json
{
  "charge": {
    "description": "Charge in coulombs producing the electric field.",
    "type": "int",
    "default": 8.854e-12
  },
  "distance": {
    "description": "Distance from the charge in meters where the field is being measured.",
    "type": "int",
    "default": 8.854e-12
  },
  "permitivity": {
    "description": "Permitivity of the space where field is being calculated, default is 8.854e-12.",
    "type": "float"
  }
}
```

对应的期望调用（`answers`）是 `{"charge": 2, "distance": 3}`——**没传
`permitivity`**。

**三个字段分别是什么**：

| 字段 | 语义 | 这条记录里的事实 |
| --- | --- | --- |
| `description` | 给模型看的**自然语言说明**，非机器可约束 | `permitivity` 的说明**明确写了** "default is 8.854e-12" |
| `default` | **机器可读**的"不传时用什么值" | `permitivity` **没有**；`charge` / `distance` **有**，都是 8.854e-12 |
| `required` | **机器可读**的"必须传" | **整份记录、乃至全语料 168870 份工具定义里，一个都没有** |

**三重矛盾叠在同一条上**：

1. **描述与 schema 打架**：`permitivity` 说它有默认值，schema 里没有。
2. **值落在了错的参数上**：8.854e-12 是**真空介电常数（ε₀，单位 F/m）**，
   把它当 `charge`（库仑）或 `distance`（米）的默认值，**物理上说不通**。
   这不是"作者忘了写"，是**值写错了位置**。
3. **类型也不吃这个值**：`charge` / `distance` 的 `type` 是 **`int`**，
   而默认值是小数 `8.854e-12`。

**所以这条样本的原始判定是"agent 漏填必填参数"（能力问题），
正确答案是"数据源 schema 写错了"（数据源的账）。** 形态一模一样，结论相反。

**这就是我说的"比漏标更硬的证据"**：漏标还能用"作者疏忽"解释，**"值在、
但贴错了地方"解释不通**。全量下来这类只有 **2 个参数位**
（`calculate_electric_field.permitivity` 258 次、
`mean_confidence_interval.confidence` 83 次），其余 19 项是"漏标 default"。
两类分开报，因为**改法不一样**（见 Q14）。

### Q14. `required=true` 与 description 冲突时谁优先（红旗：把"模型合理利用默认值"误判成数据源矛盾，349 条可能大面积误杀）

**这一条我分三层答，第三层是核心。**

**第一层（事实纠正）：这道冲突在本批不存在。**
该数据集 **168870 份工具定义里，带 `required` 字段的是 0 份**（全量扫出，
报告第八节由脚本自己数出来）。所以"`required=true` vs description"这种
冲突**一次都没出现过**。

**第二层（我的盲区，如实交代）：如果真出现，我识别不了。**
我的 `required_params()` 判据是"**没有 `default` 的参数就算必填**"——
它**根本不读 `required` 字段**。所以如果某天数据源写了 `required: true`
而参数没有 `default`，我会判成"必填没传"（形态对）；但如果它写了
`required: true` **并且** description 说"有默认值"，我**不会**识别出这是个
矛盾，我会按 description 说它有默认值去判。**这是我规则的已知盲区。**

**第三层（核心：我不需要赢这场优先级之争，就能给出正确处置）。**

你的红旗说"把模型合理利用默认值误判成数据源矛盾，349 条可能大面积误杀"。
**这个方向的风险我认，但我把处置设计成对两种读法都成立**：

```
读法 A（我对）：description 承诺了默认值 → 模型省略是合理的
                → 错的是 schema 没写 default → 动作：改 schema，样本留

读法 B（你对）：模型应该显式传所有参数
                → 这条样本确实不完美 → 动作：改 schema 让它明确，
                   同时把这条样本标进人工队列重标
                → 仍然不是"丢"
```

**两种读法下，动作都是"动 schema"，都不是"丢样本"。** 因为：

> **丢样本不可逆，改 schema 可逆。在两种解释都成立的情况下，选可逆的那个。**

这不是在回避优先级问题，这是**把优先级问题从执行路径上摘掉**。而且
还有一层实际约束：**同一份 schema 的问题会在很多条样本上重复出现**
（`permitivity` 那条 258 次）——**修一处 schema，258 条样本的歧义一次性消失**；
而丢 258 条样本，什么都解决不了（下一个用这个工具的人照样中招）。

**至于"大面积误杀"实际发生了没有**：改判后 `discard.jsonl` = **0 条**。
不是因为我更准了，是因为**我把"没把握"的去处从 `丢弃` 改成了
`待修 schema` / `需人工`**——两个都不丢数据。

### Q15. `spin → timeout → env_timeout → 不算失败`，归因是不是太粗暴

**是。这一条我承认，而且这是五个红旗里唯一"未修"的。**

现状（`triage.py` 超时判定）：

```python
if "timeout" in flat or "timedout" in flat or "超时" in flat:
    cat = CAT_ENV_TIMEOUT
```

**粗暴在哪，我讲清楚**：

1. **只有一个信号**：报错文本里出现 timeout 字样。**不看别的。**
2. **`timeout` 有多种成因，我只判一种**：
   - 沙箱/网络抖动 → 环境问题（我的判定）
   - **agent 进入死循环、自己把时间耗光** → **这是 agent 策略问题**
   - 工具实现本身慢 → 工具侧问题
   - 上游依赖挂 → 依赖问题
3. **后果不对称**：`env_timeout` 判成 `⊘ 不算失败`，样本**既不进 train
   也不进 discard**。所以判错的后果是"一条负样本没被标出来"——**漏报，不误杀**。
   这也是它优先级排后、我先修误杀类规则的原因。

**修法（还没写，但方案是具体的）**：timeout 要**多证据**才敢判环境：

| 证据 | 说明 |
| --- | --- |
| 耗时分布 | 该轨迹的耗时是否接近阈值（贴阈值→像真超时） |
| 重跑一致性 | **重跑一次还超时 → 不是抖动，是策略/实现问题**（这是最硬的一条） |
| 调用序列 | 超时前是否有重复调用（有 → 疑似死循环） |
| 步骤位置 | 发生在第一个工具调用 vs 第五个，含义不同 |

**成本如实**：多证据意味着**要重跑**，重跑要真实执行环境——而本批语料
**没有执行反馈**（我只有期望调用，没有实际执行），所以**这个修法在本数据集
上无法验证**。这是我把它列为"未修"而不是"已修"的原因：**写了也没法在真实
数据上证明它对**。

### Q16. 除零真的总是参数错误吗

**不是。`param_error` 这个类名比它的判据更自信，这是个真实的缺陷。**

现状：报错文本命中 `参数` / `param` / `invalid` / `argument` / `outofrange`
就判 `CAT_PARAM_ERROR` → 处置 `✗️ 丢弃`。

**除零的例子拆开看，至少有四种成因**：

| 成因 | 该怪谁 | 处置 |
| --- | --- | --- |
| 模型给了 `0` 作分母 | agent | 丢弃 |
| 数据里的分母字段本身就是 0（脏数据） | 数据源 | 修数据 |
| 工具实现没做边界检查 | 工具实现 | 修工具 |
| 上游工具返回了 0 | 上游 | 修上游 |

**我判不出这四种**，因为**我手上只有报错文本，没有执行上下文**。
所以我说：`CAT_PARAM_ERROR → ✗ 丢弃` 这条映射的**证据强度不足**。

**但这里有个把我兜住的机制**（不是我事后找补，是设计时就在的）：
`CAT_PARAM_ERROR` 的关键词表里，`参数` / `param` / `invalid` / `argument`
**都是相当窄的词**——而我的适配器产生的 issue 文本是
`missing required` / `unknown argument` / `schema contradiction` 这些
**结构化短语**，它们**落到 `argument` 上**……

等一下。这里我得**现场核一遍**，因为它直接决定 43 条是不是被误丢。

> **核实结果**：`missing required: xxx` 折叠空白后是 `missingrequired:xxx`，
> **不含** `param` / `invalid` / `argument` / `outofrange`，**也不含**
> `notfound` / `timeout`——所以它落到兜底类 `CAT_STEP_ERROR` → `⚠️ 需人工`，
> **不是丢弃**。全量 43 条 `missing required` 全部如此。
>
> 所以**当前真实语料上没有一条因除零类判据被丢**——`✗ 丢弃 = 0` 印证了这点。

**结论**：这个映射的证据强度确实不足，**但它的实际影响被兜底类挡住了**
（我的结构化措辞恰好绕开了那些宽关键词）。**这不是我有意设计的，是运气。**
所以我把 `CAT_PARAM_ERROR → 丢弃` 列为**需要收紧的映射**：在拿不到执行
上下文的前提下，它应该改成 `⚠️ 需人工`；只有当"除零/参数错"能在**轨迹自身
内部**被证实时（比如 `arguments` 里真的写着 `0`），才允许丢弃。

### Q18. 15 类根因的优先级谁定的？同一轨迹命中多类怎么裁决？证据链怎么避免自证？

**三个问题，逐个。**

**(a) 优先级谁定的？——我定的，但依据是"证据强度"不是"重要性"。**
`triage.py::diagnose()` 是**短路判断**，顺序如下（越靠前越先判）：

| 序 | 判据 | 为什么排这 | 证据强度 |
| --- | --- | --- | --- |
| 1 | 槽位出处（`ungrounded_slot`） | 不需要 golden 标签，生产环境能跑 | 高（问句里找得到找不到，可复核） |
| 2 | `schema contradiction` | **必须排在硬错误之前**——否则会被笼统归成"参数写错" | 高（schema 两字段之间的事实） |
| 3 | 硬错误关键词（timeout / not found / param） | 依赖报错文本 | 中 |
| 4 | `retry_storm`（重复调用） | 幂等性是工具属性，我拿不到 | 低（本批 0 命中） |
| 5 | `hallucinated` / `mismatch` | 需要 golden 或问句对照 | 中 |
| 6 | `step_error`（兜底） | 认不出来就老实说认不出来 | —— |

**"排错顺序就会被笼统归成参数错误"这条是真实踩过的坑**：如果 `schema
contradiction` 排在"报错文本含 param/argument"之后，那 1286 条会被吞进
`param_error`，方向整个反过来。**顺序本身就是判据的一部分。**

**(b) 同一轨迹命中多类怎么裁决？——短路取第一个，但我把"多命中"记下来。**
`diagnose()` 短路返回，所以一条轨迹只有一个根因。但**下游不丢信息**：
`run_trust_filter.py` 逐步骤、逐 issue 记 `by_kind`，所以
**1491 个问题条数 > 1351 个命中样本数**——差额就是"一条轨迹命中多类"的部分。
报告第五节专门标了单位，防止有人拿两个数对不上来质疑。

**(c) 证据链怎么避免自证？——三条，都有代码位置。**

1. **证据是原始数据，不是我的判断**：每个 `Diagnosis.evidence` 存的是
   **报错原文 / schema 原文片段**，不是结论的复述。
   `row` 号落进 `golden`，可回到原始 JSON。
2. **探针与判断分离**：`probes.py` **只观测不判断**（拿得到信号就返回，
   不做归因）；所有判断集中在 `triage.py` **一个函数**里。
   好处是**判断层可以整体替换**（换成 LLM 归因器，或换成别的规则集），
   而观测层不动——**这本身就是"可被证伪"的结构**。
3. **不写结论进 golden**：`golden = {source, row, unlabeled: True}`。
   如果 golden 里写着"这条该判 schema_contradiction"，那评测就是自证。
   （`tests/test_xlam_adapter.py` 有一条测试专门钉这个。）

### Q19. UNKNOWN 降级比例多少

**先给数，再给两个分母（这个细节很重要）：**

```
兜底类（CAT_STEP_ERROR）条数 = 65

按"命中样本"算：65 / 1351 = 4.81%   ← 规则在"有问题的那部分"里的覆盖率缺口
按"全部样本"算：65 / 60000 = 0.108% ← 规则在全量里的覆盖率缺口
```

**两个都对，回答的问题不同**：

- 被问"你的归因规则好不好"→ 用 **4.81%**（分母应该是我有判定的那些）。
- 被问"业务影响多大"→ 用 **0.108%**。

**报哪个，取决于在回答什么问题——我两个都摆出来，不挑对我有利的那个。**

**但这个比例低不代表规则强**，原因见 Q17：58649 条未命中里可能藏着大量
我覆盖不到的脏，而**这个数我无法测量**（无标签）。

**"多则不可用、少则过拟合"这个判断我不接受**——因为它假设了"UNKNOWN 比例"
和"规则质量"之间有单调关系。**在无标签数据上它们没有可测的关系**：
UNKNOWN 低可能是因为规则真的准，也可能是因为**我的规则只查我查得到的那几项**
（名字、参数名、参数集，就这三项）。**后者更可能是真的。**

## 4. 工程与训练集成（Q20–Q24）

### Q20. `findata` 会不会被喂进 loss？SFT collator 怎么剥离？

**这是本项目工程上最要命的一格，我实测过：**

```python
# data/filtered/train.jsonl 第一条
top-level keys: ['findata', 'id', 'messages', 'row', 'source', 'tools']
#   → findata 是 messages 的【兄弟键】，不在 messages 里面
```

```json
{
  "id": "xlam-0",
  "source": "Salesforce/xlam-function-calling-60k",
  "row": 0,
  "messages": [
    {"role": "user", "content": "..."},
    {"role": "assistant", "tool_calls": [{"type": "function", "function": {...}}]}
  ],
  "tools": [...],
  "findata": {"verdict": "✓ 正样本", "root_cause": "ok", "evidence": [], "suggestion": ""}
}
```

**关键点**：

1. **判定结论是 `messages` 的兄弟键，物理上不在 loss 的输入路径上。**
   标准 SFT collator（`DataCollatorForLanguageModeling` /
   `trl.SFTTrainer`）走的是 `messages` 字段，`findata` 它根本读不到。
   **这不是靠"记得剥离"，是靠结构。**
2. **`tools` 也是兄弟键**——这一条同样重要：工具定义该进 prompt（作为
   可用函数列表），不该进 loss 的 label。位置由下游按需拼。
3. **风险仍在**：如果谁写了个
   `[json.dumps(x) for x in row.values()]`，就会把 `findata` 拼进去。
   **我没法从结构上禁止这件事**，只能靠文档 + 这条实测记录提醒。

**为什么不做成"strip 干净、只剩 messages"**：因为判定必须**跟着样本走**。
分开存（样本一个文件、判定一个表）看起来更干净，但**会漂移**——两张表在
流水线里会错位，而**这种错在训练跑完之前不会有任何报错**。用兄弟键是
**用一点点下游自觉，换掉一整类静默错**。

### Q21. manifest 版本化

`data/filtered/manifest.json` 里有**可复现三元组**：

| 字段 | 值 | 为什么必须有 |
| --- | --- | --- |
| `code_commit` | `git rev-parse HEAD`（拿不到就写 `unknown`，不装） | 规则代码会变 |
| `rules_version` | `triage.RULES_VERSION`（现为 `2026-09-18.2`） | **规则集单独版本号**——改一个关键词就该跳版本，不然旧的过滤结果无法解释 |
| `data` | 文件 sha256 前 16 位 + 字节数 | **公开数据集会被作者修订**，只记代码版本复现不了旧结果 |

**为什么 `rules_version` 要单独一个而不是用 commit**：因为规则集会被**整体
替换**（换成 LLM 归因器）——那时 commit 变了，但"数据是不是同一批判定逻辑
处理的"这个语义需要独立追踪。

`manifest` 里还有 `note` 字段，把口径写进**产物本身**（而不是只写在文档里）：
「没查出问题 ≠ 确认正确」「`not_failure` 不是负样本」「`schema_defects`
不该作废」。

### Q22. 百万级怎么办？`$ref` / `allOf` / `anyOf` 支持吗？

**先答支持性，答"不支持"，而且这是设计选择**：

- **不支持 `$ref` / `allOf` / `anyOf`**。该数据集的 schema 是**扁平的**
  `{name, description, type, default}` 字典，没有嵌套结构，
  所以 `misplaced_defaults()` / `required_params()` 都是**一层的**。
- **不支持不是遗漏，是"按数据形状设计"**——但**因此我的适配器只对这个形状
  有效，这是边界**。换成嵌套 schema，我的三层判定（名字在不在、必填有没有、
  参数名认不认）需要重写。**不假装通用。**

**再说真正的百万级瓶颈——不是 schema 特性，是 schema 身份。**

全量实测：**3605 个工具名里，296 个（8.2%）有多份互不相同的定义**。

```
search        77 种定义
getorderbyid  15 种
getpetbyid    14 种
loginuser     13 种
geocode       10 种
```

举个最直观的：**`time_series` 这个名字对应 4 个完全不同的 API**：

```
{'base': 'USD', 'end_date': '2022-01-20', 'start_date': '2022-01-10', 'symbols': 'BRENTOIL'}
{'format': 'json', 'interval': '1day', 'outputsize': 30, 'symbol': 'AMZN'}
{'format': 'json', 'is_from': '2022-01-28', 'month': '8', 'offset': '', 'symbol': 'CL', ...}
（还有一个 XAU 的）
```

**这对我的实现是硬伤**：我处理同名多定义的方式是"**任一份 schema 能解释
这次调用就放行**"（这条容错是必需的——不加它曾误报 45 条 `unknown argument`）。
但在百万级数据上，同名定义越多，**"总有一份能解释"的概率越高**，
于是**我的系统会系统性少报**。**这是我当前实现最大的可扩展性缺陷，
不是性能问题。**

**百万级的其他三件事（这些是真的做了）**：

1. **内存**：`ijson` 流式读（96MB 文件 `json.load` 一次就能把开发环境撑爆，
   实测连 echo 都打不出来）；`SplitWriter` 边判边写，2 万条和 200 万条
   内存占用一样。
2. **耗时**：全量 6 万条 / 100011 次调用 **16 秒**（单线程查表）。
   线性外推到百万级约 **4.5 分钟**，不需要改架构。
3. **产物格式**：JSONL 一行一条，可追加、可并行分片。

**没做的**：真正的分布式、断点续跑、schema 注册中心（把"同名多定义"归一化）。

### Q23. 沙箱的 fork bomb / 网络 / 文件系统 / 密钥；拉不到镜像就不做，是合理边界还是逃避

**四个问了，我一个都没做到，直接列表**：

| 威胁 | 现状 | 能不能做到 |
| --- | --- | --- |
| fork bomb | **不防** | 进程级隔离防不住，必须 cgroup / job object |
| 网络出站 | **不限制** | 需 netns 或防火墙规则 |
| 文件系统 | **不限制**（子进程能读写本机） | 需 mount namespace / 沙箱目录 |

**"拉不到镜像就不做，是合理边界还是逃避"——这个问题问得准，我的答案是：
一半边界、一半逃避，我分得开。**

**所以我把它记为"能力缺口 + 优先级取舍"，不记为"环境边界"。**

**这一条还有一层意义**：沙箱是本项目里**唯一一个"我明确知道没做完、

## 6. 收尾（Q33–Q37）

### Q33. 最薄弱一环

**三个候选，我按"会不会让整件事站不住"排序：**

1. **【最薄弱】没有任何人工抽检 / 人工一致性数字。**
   我今天报的所有数（1351 命中、1286 待修、21 个参数）**全部是机器判的，
   没有一条经过人工确认**。整个系统的可信度建立在一个**未经验证的前提**上：
   "我的规则判对了"。**这个前提我一次都没测过。**
   为什么没做、以及"我一个人标会让 κ 虚高"的道理见 Q9。
   **要补的**：一个不知道规则细节的人，随机 100 条，三分类盲标，算 κ。
   成本约半天。**这是第一优先。**

2. **模型侧收益完全没测。**
   "过滤后训练效果更好"——**这句话我一次都没验证过**，本机跑不了有意义的
   对照。所以这个项目**只能主张"数据变干净了"，不能主张"模型变强了"**。

3. **内容安全零覆盖**（Q31）。产物不能当合规数据集交付。

**共同点**：三条都是"我证明了输入侧的属性，没证明输出侧的后果"。
**这是这类项目最容易自我欺骗的地方**——因为输入侧的指标很好算。

### Q34. 重做砍什么、补什么

**砍（三条，都是"删"）：**

1. **7 个旧线 MCP 工具**（`health_check` / `dashboard` / `validate` /
   `metric_query` / `ask` / `list_metrics` / `execute_metric`）——
   全部与当前主线无关（Q24 的表）。保留 2 个有真实宿主验证的。
2. **`src/findata/agentops/sandbox.py` 的 Windows 分支**——`MEMORY_LIMIT_SUPPORTED`
   在 Windows 上恒为 False，本地永远走不到有效路径。**沙箱应该整体搬进
   CI（Linux）**，本机那套"看着有其实防不住"的实现留着只会误导。
3. **`required_params()` 里"没 default 就算必填"的隐含假设**——不是删函数，
   是删**它对结论的直接决定权**：这条判据必须显式标注为"我设的口径"
   （已经做了），且不允许单独触发 ✗ 丢弃。

**补（也是三条，按优先级）：**

1. **人工抽检 + κ**（见 Q33-1）。**不加新功能，先把最基础的前提验了。**
2. **给 `triage` 加"证据强度"字段**，让 `✗ 丢弃` 只在**轨迹自身内部可证**
   时触发（Q16 的除零问题、Q15 的 timeout 问题都指向同一件事：
   **处置的风险等级应该由证据强度决定，而不是由根因类别决定**）。
3. **v3.0 主线加一个 MCP 入口**（"质检一批轨迹"），让主线在产品形态上有
   和旧线同等的可达性。

**为什么"砍"排在"补"前面**：现在最大的问题不是功能不够，是**同一份仓库里
两条主线并存**（红旗 #5）。砍完，Q7 那个问题就不存在了。

### Q35. 规则与人工冲突信谁

**信人工，但要求人工的判定也是"可复核的事实"而不是"意见"。**

具体规则，我分三种冲突：

| 冲突形态 | 信谁 | 为什么 |
| --- | --- | --- |
| 规则报问题 + 人工说没问题 | **信人工** → 这条进"规则误报"清单 → **修规则** | 误报是规则的账 |
| 规则没报 + 人工说有问题 | **信人工** → 进"规则漏报"清单 → 加规则 or 承认覆盖不到 | 漏报是覆盖率的账 |
| **规则报 A 因 + 人工说 B 因** | **不算冲突，是升级信号** | 说明这个观测有**多种解释**，而我的优先级把其中一种排前面了 → **该改的是裁决顺序（Q18a）** |

**第三种是最有价值的**——它不是"谁对"，它说明**我的证据强度排序错了**。

**两个前提（不然"信人工"是空话）**：

1. **人工要盲标**：标的人不能先看规则说了什么。否则他会顺着规则想，
   冲突永远不会出现——**这比没有人工抽检更糟，因为它产生了一个假的
   一致性数字**。
2. **冲突要留证据**：每次冲突都落一笔（规则判定 / 人工判定 / 出处行），
   **累积起来就是我的规则集最真实的改进方向**。

**现在这套机制的现状**：⚠️ **`review.jsonl`（65 条）就是人工队列的设计，
但它没有配套的标注流程和冲突记录**——**队列有了，接队列的人还没接上。**
所以"证据不足交人工"这个设计**目前只走完了前半段**。

### Q36. 怎么证明归因不是循环论证

**这是整份清单里最好的一问。我的答案分四层，从弱到强。**

**第一层（最弱的辩解，我不靠它）**："我的语料是别人的，所以不是自证。"
——**不够**。语料是别人的，但**规则是我写的**，我完全可以写一套只命中
别人的语料、却不为真的规则。

**第二层（结构性证据）**：归因依赖的**每个事实都来自数据源的两个字段之间**，
不来自我的判断：

```
permitivity 的 description 说 "default is 8.854e-12"
permitivity 的 schema     没有 default
charge/distance 的 default 是 8.854e-12
     ↑ 这三条都是 schema 里的字面内容，可逐字复核（row 号在产物里）
```

**这不是"我判断它矛盾"，是"它自己矛盾"。** 我做的只有"发现"，
没有"解释"。

**第三层（可证伪性）**：我的判断**能被外部证据推翻**，而且**给定了推翻方法**：
把 `permitivity` 的 `default` 补上 → 那 258 条应该全部消失。
**这是可执行的预言。** 如果补上之后还有样本被判问题，说明我的规则里有别的
东西在冒名顶替——**这就是证伪路径**。

**第四层（最强，也是最有说服力的）：我做了一次自证的反面操作。**

**我删掉了一个探针，因为它命中的东西经核查是假的。**
（类型/默认值冲突探针，全量命中 2162 条 → 逐条核出是表示层约定：
89.1% 的 `default` 本就是字符串 `"10"`，`type: int` + `default: "10"`
是约定不是矛盾 → **删除，并把这次否定写进报告第八节**。）

**一个循环论证的系统不会删自己的探针**——它的每条规则都在为"我很准"
这个结论供血。**能自我否定，才有可能在自我校准。**

**第五条（补一个我之前没说清的）：循环论证风险真实存在的地方，我标出来了。**
`probe_retry_storm`（重复调用探针）**在本批 0 命中**——这意味着
**它从未被真实数据验证过**，它的判据（"同名且同参数重复 = 异常"）是
**我从常识推出来的，不是从数据里学到的**。这就是循环论证的入口，
所以我按项目的"拆表法"**先不动它，留作开放问题**，并且明确写它"未被验证"。

**什么情况下我承认自己翻车**：如果有人拿一批**带人工标签**的轨迹跑我的
系统，误杀（本该留的被判 ✗）**超过 5%**——那说明我的"少报"策略还不足以

### Q37. 要一个具体数字：脏率从多少降到多少 + 模型指标提升多少

> 这个项目证明了**输入侧的数据属性**（哪些样本的调用与 schema 不相容、

**这是本项目的最大空洞，也是我把它列在 Q33 第一位的原因。**
