# 正职岗日常职责 ↔ 本项目产出 ↔ 缺口

> 2026-09-22。**判据：每条职责要么能指到本仓库的一个文件 / 一条命令 / 一个数字，
> 要么明确写成缺口。** 不许出现"基本做了""大体覆盖"这种既不能证实也不能证伪的话。
>
> 目的不是"我做了什么"，而是回答**那个岗位每天做的事，我做到第几条**。
> 岗位证据的出处见 [`docs/business-case.md`](business-case.md) §2.1。

## 0. 先说结论

四个真实 JD 的职责拆成 **18 条可验收的动作**，现状是：

| | 条数 | 意思 |
| --- | ---: | --- |
| ✅ 做到（能指到产物） | **10** | 有文件、有命令、有实测数字 |
| ⚠️ 做到一半（产物在，但形态不对/规模不对） | **5** | 见 §2 的"缺口"列 |

**最要紧的一条**：18 条里**唯一真正"像 demo"的地方是规模**——实验语料里的工具定义
是我手写的（4 真实实现 + 23 个只有定义的沉默工具），而真实生产里是**几千个**。
这一条已经在补（抽 100–200 台公开真实 MCP server 的定义）。

| --- | --- | --- | --- |
| **P0** | 真实规模（手写 27 个定义 → 100–200 台公开真 server） | 18 条里唯一"像 demo"的地方（C2）；不补则所有规模相关结论都只能算"实验条件下的量" | 新语料有指纹、来源可引用、四臂在新语料上跑完、结论按新规模重报。**进度**：语料已到位（47 台 / 230 工具，抓取与指纹核对通过）；**卡在推理侧**——230 个定义（82,300 字符）超过本机上下文窗口，冒烟时 `prompt_tokens` 卡在 4096 且工具调用掉到 0（r5.0 §3.12.1，**未验证假设**）。所以"四臂在新语料上跑完"要先解决窗口，否则跑出来的是截断后的读数 |

| **P1** | `baseline.json`（可回滚基线） | 现在基线散在账单里，缺"机器可核对的基线" | 一条命令产出 + 一条命令核对（不同即非 0 退出） |

| **P3** | 延迟侧配对报（A3） | 最容易被追问"你省了 token 但拖慢了吗" | 同口径给出每任务耗时的配对分布 |

## 5. 这张表怎么用（面试时）

1. **先给岗位定义，再给自己进度**——顺序反了就变成"你看我做了多少"。
2. 被问"这是不是 demo"时，**指第 2 节主表的坐标**（A4 那一行有完整的取舍曲线，
   A6 那一行有三重指纹），比形容词有用。
3. 被问"还有什么没做完"时，**直接给第 4 节**——里面有 P0/P1 的排序和验收判据，
   而不是"还有很多可以优化"。
4. **第 3 节要主动讲**：说明我知道哪些不在我的射程内、为什么。
   讲不清"不做什么"的人，通常也没想清楚"做什么"。
