# 产品化终局目标与差距清单

> 建立于 2026-09-23。**这份文档是"做到什么算完成"的唯一清单**，不是路线图
> （路线图管"下一步做什么"，在 `docs/ROADMAP.md`）。
>
> 用法：每条目标都带**可验收判据**（能被外部人核对的判据）与**当前状态**。
> 状态只允许四选一：`已达成` / `部分` / `未开始` / `无法核对`。
> **不允许出现"基本达成"** —— 那是让清单失去判别力的写法。
>
> 口径标注：`[实测]` = 本次核查当场算出来的；`[读取]` = 从文件内容读到的；
> `[未核实]` = 我没有证据，不许当事实用。

## §1 终局定义：先把"产品是什么"定死

### 1.1 一句话终局

> **一个开源 CLI：喂进 agent 的运行轨迹，吐出一份现成网关能吃进去的
> 上下文/工具预算策略（`policy.json`），并附一份"这个策略没伤到结果"的
> 配对验证报告（`report.md`）与一份可回滚的基线指纹（`baseline.json`）。**

三个交付物各自回答一个问题，缺一个都不算完成：

| 交付物 | 回答的问题 | 谁用 |
| --- | --- | --- |
| `policy.json` | 该允许/禁止哪些工具、上限是多少 | 现成网关（`ubie-oss/mcp-proxy`、`mcp-shield` 这类）直接吃 |
| `report.md` / `report.json` | 这个策略**有没有让结果变差** | 团队里做决策的人 |
| `baseline.json` | 语料·代码·策略·模型指纹，能不能核对、能不能回滚 | 复核的人 |

**定位的关键取舍：不造网关，给网关产出策略。** 理由见 §5。

### 1.2 ⚠️ 当前最大偏差：仓库里同时存在两个产品，而资源武装的是老的那个

这是本次核查最重要的发现，一切差距都排在它后面。

`[实测]` `src/findata/` 共 18,642 行，按子包归类：

| 归类 | 行数 | 占比 | 子包 |
| --- | ---: | ---: | --- |
| **当前主赛道**（v3.0 轨迹质检 / v4.0 上下文经济学） | **6,978** | **37.4%** | `agentops` `contextbudget` `economist` |
| **已降级/封存的老赛道**（v0.x–v2.2 可信数据/A 股） | **11,664** | **62.6%** | `agent` `api` `chatbi` `core` `domains` `dq` `eval` `generic` `mcp` `observability` `report` `semantic` |

而**产品面全在老赛道上**（`[读取]`）：

- `Dockerfile` 最后一行是 `CMD ["python", "-m", "findata.cli.serve"]` → 起的是
  老赛道的演示看板；
- `release.yml` 推 ghcr.io 镜像，推的是这个；
- `test.yml` 的 `eval-gate` 守的是 `eval_golden.py` / `run_eval.py`（语义层 + 归因层），
  `smoke` 守的是 `/v1/inspect`、`/v1/dashboard`；
- `pyproject.toml` 的 `version = "2.2.0"`、`description` 写的还是
  "可信数据增强模块"，**没有任何一处反映主赛道**；
- **主赛道在 CI 里没有任何门禁**：`run_context_audit.py` / `run_trust_filter.py` /
  `compare_audit_arms.py` 一次都没被 CI 调用过。

⇒ 结论：**镜像、CI 门禁、README 的产品叙事、版本号，四样都在讲老产品；
主赛道只有文档和一个 CLI 入口。** 面试官只要问一句"你的 Docker 里跑的是什么"，
这个偏差就暴露了。

**验收判据（L1 的总闸门）**：`docker run <image> --help` 能跑出**主赛道**的
用法；`ghcr.io/...:<tag>` 的镜像内容与 README 首屏讲的是同一件事。
状态：`未开始`。

### L2 健壮与高可用（"它会怎么坏，坏了怎么办"）

> **口径说明**：CLI/库的"高可用"不等于 `99.99%` SLA。它等于
> **①不会挂死 ②不会毁用户状态 ③坏了能诊断 ④部分失败会如实报**。
> 下面每条都是这四件事之一。

| # | 目标 | 可验收判据 | 现状 | 差距 |
| --- | --- | --- | --- | --- |

## §3 差距总清单（按优先级排序）

排序依据两条：**① 不做的后果是否致命 ② 是否能在一次改动里拿到可验证的结果**。
不看工作量——工作量不是排序依据，因为它是最不该拿来挡路的借口。

## §4 必须由**你**做的业务取舍（我给建议，决定权在你）

这五条不是技术问题，是产品判断。每条我都写了建议与理由，但**别人的答案不能算你的答案**
——面试里问的正是"你怎么想的"。

### 4.1 老赛道（62.6% 的代码）留还是不留？

- **现状**：`agent` `dq` `semantic` `report` 等 11,664 行已降级，但 Dockerfile、
  CI eval-gate、README 大部分叙事、演示站都挂在它上面。
- **选项 A**：保持现状，把它写成"领域包 1（已封存，作为通用性证据）"。
- **选项 B**：整体移到一个独立仓库/分支，主仓库只留主赛道。
- **我的建议：A，但把产品面全部搬到主赛道。** 理由：老赛道是这个项目
  "这套方法不是只会一件事"的证据，删掉可惜；但它**必须停止占用产品面**
  （镜像、CI 门禁、README 首屏、版本号）。判断标准一句话：
  **老赛道可以留在仓库里，但不能留在"首页"和"闸门"里。**
- **需要你决定的**：Dockerfile 起的到底应该是哪个东西？

### 4.2 产品形态：CLI 还是"库 + 策略产出"？

- 你已定：开源 CLI 工具。
- **但需要再确认一处**：CLI 是"跑一次出三个文件就走"，还是"常驻服务，网关来轮询"？
- **我的建议：跑一次出文件。** 常驻服务会立刻把项目拖进 L2 的一大半
  （并发、限流、SLO、部署），而收益是零——网关自己就会常驻。
  这也是"不造网关，给网关产出策略"的同一条逻辑。

### 4.3 质量侧结论"没有分辨力"这件事，怎么讲？

- **现状**：R5.2 头号结论的 token 侧很硬（−52.0%，符号检验 p=2.46e-07，
  30 正 / 2 负）；质量侧 k<6，**测不出差异**。
- **选项 A**：只报 token 侧，质量侧写"未测得"。
- **选项 B**：把"我们做了分辨力下限检验，发现自己的对照没有效力"本身当结论讲。
- **我的建议：B。** 理由：这是这个项目**最稀缺的东西**——大部分人只报有利的一半。
  但必须配一句话说清代价："**这意味着我不能声称裁剪不伤质量，只能说没测到伤害。**"
  说清楚这一句，比多一个漂亮数字有用得多。

### 4.4 云端模型这条要花多少钱、值不值？

- **现状**：所有质量侧结论都只是本机 7B/3B 口径，面试必被质疑"换大模型还成立吗"。
- **建议**：按**最小调用量**跑（你之前也是这个决定）：32 任务 × 4 臂，
  只跑一次，不作迭代调参。理由：这一批的用途是**回答"换模型会不会翻结论"**，
  不是去刷榜；一次就够。
- **需要你决定的**：预算上限；以及是否接受"跑出来结论翻转"这个可能
  （接受它，因为这正是诚实的代价）。

### 4.5 目标用户是谁？

三个候选，选一个当主叙述，其余当"也能用"：

| 候选 | 他的痛点 | 你要额外提供什么 |
| --- | --- | --- |
| ① 自己搭 agent 的独立开发者 | 工具越加越多、账单涨、模型开始选错工具 | 离线示例 + 一份 `policy.json` 直接能给网关吃 |
| ② 平台/基础设施团队 | 要给内部 agent 定预算与准入策略 | 可复核的基准 + 指纹 + 回滚 |
| ③ 做 agent 训练数据的人 | 要判断轨迹能不能喂训练 | 轨迹质检那一套（v3.0） |

- **我的建议：① 当主叙述，② 当"这是它能长成什么"的延伸。** 理由：
  ①的口子最小、能自己验证（你自己就是用户），②需要组织信任，不适合当第一个用户。

## §5 明确不做（取舍的正面表述）

**"不做什么"比"做什么"更能看出判断力。** 下面每条都是主动放弃，不是没来得及。

| 不做 | 理由 |
| --- | --- |
| **不造网关 / 不写 proxy** | 网关是成熟的、有人维护的、要处理并发与鉴权的组件。造它是把项目拖进一场必输的军备竞赛，而我们真正稀缺的是"能证明策略没伤结果"的闭环 |
| **不做 SaaS / 不做账号体系** | 一旦有账号就有合规、计费、客服，这些都不产出洞察 |
| **不接闭源付费 API 进 CI** | 依赖外部付费服务的 CI 无法被别人复现——那正好否掉了 L4.1 这个最强项 |
| **不自研"模型路由"** | 竞品 System One 已经把这条路占了且不是我们的差异化；复刻其协议必须标注"协议仿真，不是本体" |
| **不做 LLM 质量打分** | 用另一个模型给轨迹打分，是把不可验证引入到裁判位置。我们用的是**确定性量**（token / 成本 / 成功率） |
| **不做花哨前端** | 可视化够用即可 |
| **不做实盘 / 交易信号** | 永久红线 |
| **不做 K8s / 多地域 / 99.99% SLA** | 这些是"服务型产品"的要求。我们的形态是 CLI，硬套会变成过度设计 |
