# 开发路线图 v4.0 · Agent 上下文与工具预算的自治策展（2026-09-18 第二版重定向）

> ## 主线重定向 v4.0 —— 新方向只看这一节
>
> **用户给的选择标准（原话）**：「尽量是一个**通用 agent**、**受众面足够广**的，
> **面向需求而不是面向已有的技术轨迹**决定下一步开发」。
>
> 上一版（v3.0 训练数据质检）是**技术轨迹驱动**的：我的论据是"复用率 70%"、
> "这是我唯一不可替代的能力"。**这个论据方式本身是错的**——它回答的是
> 「我能做什么」，不是「谁需要什么」。更糟的是 v3.0 的处置动作违反了我自己
> 立的判据（项目铁律：处置要看「**能不能给出可执行动作**」）：大多数 agent
> 开发者的工具定义来自第三方 MCP server，**他们改不了**，我给出的"schema
> 补丁"对他们就是不可执行的动作。
>
> **本版按需求侧证据重选方向。** v3.0 不推翻，降为领域包（见下）。

## 零、为什么是这个方向（全部是外部证据，不是我的偏好）

### 需求侧的硬数字

| 证据 | 数字 | 来源 |
| --- | --- | --- |
| agentic 每任务 token 成本 vs 普通 chatbot | **5–30 倍** | Gartner 2026-03 |
| 组织超出原始 AI 预算预测的比例 | **73%** | FinOps Foundation 2026 |
| 重复发送的上下文占 agent 账单 | **约 62%**（单一最大优化目标） | Vantage 2026 / Iternal 审计 30 个团队 |
| 平均月 AI 支出变化 | **+36% → 约 $85,500**；月支出 >$100k 的组织占比 **20% → 45%** | CloudZero 调查 500 位工程负责人 |
| 预计被取消的 agentic 项目 | **>40%（2027 年底前）**，首因是成本 | Gartner 2025-06 预测 |
| 单个 runaway 事故 | LangChain 多智能体无限循环 **11 天 / $47,000** | 2026 广为引用 |
| 编码 agent 成本 | 每工程师每月可达 **$2,000**；单任务 1–3.5M token | 行业审计 |
| 前缀缓存的价差 | Anthropic 缓存输入约 **10%** 基准价，OpenAI **50%** | provider 定价 |

### 工具膨胀侧的硬数字

| 证据 | 数字 |
| --- | --- |
| 工具数 vs 选择准确率 | **50 个 → 84-95%**；**200 个 → 41-83%**；**740 个 → 多数模型接近 0** |
| 列表位置效应（Lost in the Middle） | 中间 40-60% 位置准确率降到 **22-52%**，两端 31-32% |
| 断崖 | 有研究在 **207 → 417 工具**时非线性崩塌 |
| MCP 工具元数据占上下文窗口 | **40-50%** |
| 一个真实案例 | 12 工具 → 90 工具，选择准确率 **90 出头 → 70 出头**；隐藏 75 个后**反而更聪明** |
| 生态规模 | **4,133 个 MCP server / 11,393 个 agent 工具**，全在往上下文里塞 |
| 实际使用率 | 多数 agent 稳定只用可用工具的 **10-15%** |

### 现有解法覆盖了什么、**缺**什么（这是差异化，必须精确）

| 手段 | 代表 | 决策依据 | 缺 |
| --- | --- | --- | --- |
| 模型路由 | RouteLLM (ICLR 2025)，省 **40-80%** | **按任务类别预设** | 与"这个具体返回该不该进上下文"无关 |
| 前缀缓存 | provider 原生 | **按 token 前缀匹配** | 同上 |
| 工具检索 | RAG-MCP / AutoTool（准确率 **13.62% → 43.13%**） | **按 query 与工具描述的向量相似度** | 相似≠会被用；且不看历史使用 |
| 上下文压缩 | 滚动摘要 / 滑动窗口 | **按位置或长度** | 不看内容是否真被用到 |
| 成本面板 | Langfuse / LangSmith | **被动统计（花了多少）** | **不主动给出该改什么** |

> **共同缺口**：以上全部是**预置型/规则型**决策。
> **没有一个是从「模型在这次真实调用里实际用了什么」反推该保留什么**——
> 因为「模型实际用了哪些字段」**只能从 trace 观测，不能从文档推出来**。
>
> 而这正是本项目最硬的能力：**从真实证据出发做准入决策，不凭想象设口径。**

## 一、这不是推翻 v3.0，是同一个动作换域

本项目三版主线，内核是**同一个动作：准入决策**。

| 版本 | 问题 | 产出 | 受众 |
| --- | --- | --- | --- |
| v1 可信数据引擎 | 这个数字**能不能引用** | 徽章 + 证据链 | 数据分析师 |
| v3.0 训练数据质检 | 这条轨迹**能不能喂训练** | 五档处置 + 缺陷归因 | 做 SFT 数据的人（**窄**） |
| **v4.0 上下文策展** | 这段内容**该不该进上下文** | 策略改动 + 省下的 token 与成本 | **所有跑 agent 的人**（含只关心钱的老板） |

**核心命题「形态相同、结论相反」在上下文域照样成立**，而且是同一个错法的第四次变体：

- 一段 5,000 token 的工具返回，**看起来信息丰富（形态），实际模型只用了 3 个字段（结论）**
  → 看起来该留，实际该裁
- 上下文里**少了关键信息** vs **多了无用信息**，**症状完全一样（agent 答错），处置方向相反**
  → 一个要补，一个要裁；判据仍是 **加信息可逆、删信息不可逆 → 证据不足时选可逆的那个**

**判定档位沿用 v3.0 的五档骨架**（改判据不改结构），措辞纪律照旧
（「命中」不是「发现」；「未观测到使用」不是「无用」）。

## 二、交付物

**`findata-context-economist`**：读一个 agent 的真实 trace，输出**经过验证的**
上下文与工具策略改动，并给出三组数字：**省下的 token / 折算成本 / 成功率变化**。

```
一个 agent 的真实 trace（OTel gen_ai.* span）
   ↓ 1 观测   每个工具调用：返回的 payload 有多大、模型后续引用了什么
   ↓ 2 判定   哪些字段被真正使用（可观测）、哪些从未被引用（≠ 无用，需要证据强度分层）
   ↓ 3 提议   对具体工具的具体改动（裁字段 / 改返回 shape / 分层加载 / 改缓存边界）
   ↓ 4 验证   同一批任务改前 vs 改后重跑 → token、成本、成功率
   ↓ 5 报告   数字 + 证据链 + 不确定性 + 不可迁移的部分
```

**为什么它必须是一个 agent（规则做不到）**：
「模型是否真的用了这个字段」这件事**无法用规则表达**——它要读模型在后续步骤里的
推理与参数、要判断"这个字段被引用了"还是"只是恰好出现在上下文里"、要在证据
不足时**拒绝下结论**而不是猜。**每一步都需要推理与自省，正是一个 agent 的活。**

### v0.1 已落地（2026-09-20）

`src/findata/economist/`（`trace.py` 读输入 / `analyze.py` 判定+提议+验证 /
`report.py` 渲染）+ `scripts/context_economist.py` + console script
`findata-context-economist`。新增 **29 个用例**（`tests/test_economist.py`）。

> 措辞说明：这里写"29 个用例"而不是"N 例测试"，是为了**不被文档一致性门禁**的
> 正则当成"全仓库测试数"的另一个声明——那一条要求全仓库只有一个数（当前 458）。
> 模块级计数用"个用例"，别改回去。

五步都跑通了，**关键是第 4 步有真数字**（同一批 32 任务、同一份冻结语料）：

| 量 | 改前（27 定义） | 改后（4 活跃） | 差 |
| --- | ---: | ---: | ---: |
| prompt tokens（实测） | 224,051 | 100,843 | **−123,208（−55.0%）**，符号检验 p=2.6e-06 |
| 工具调用次数 | 52 | 53 | +1 |
| 关键词命中（弱判据） | 8 | 12 | +4，McNemar p=0.1250 |

三条方法上的决定，都是"不做就会虚报"的那种：

1. **重建必须对账**：返回原文不在 trace 里 ⇒ 用记录的参数重放，
   **字符数与记录值完全相等**才准进字段级统计（本批 52/52）。
   对不上的调用一律退出统计，不计分子也不计分母。
2. **估算与实测分开**：字符口径估算 136,348 tokens vs 实测 123,208 ⇒ **1.11×**。
   估算只用来给提案排序；这个倍数是"字符换 token"的误差量级，写进报告 §7.1。
3. **不合成单一"节省百分比"**，也**不给默认单价**——两者都会让弱证据或假设
   看起来像结论。分档（被引用 / 未观测到引用 / 不可判）+ 分项。

已知缺口（写进报告，不藏）：`after` 只含最终答复与后续调用参数（**缺模型中间
推理文本 ⇒ 只会漏判**）；分层加载省的是 payload 而**多出来的调用成本未计入**；
段切分规则跟着这批 Markdown 返回写（换 JSON 返回要换实现）。

## 四、明确不做（防止又做偏）

## 五、诚实边界（必须写清，否则又是自嗨）

1. **本机实验用的是 7B 本地模型，不是 GPT-4o/Claude。**
   - **token 侧结论可迁移**：token 数由**上下文结构**决定，与模型无关
   - **成功率侧结论不可直接迁移**：小模型对上下文噪声更敏感，
     我的"裁剪后成功率不降"**只在本地模型口径下成立**，必须原样写出来
2. **「从未被引用」不等于「无用」**——本批任务没覆盖到，不代表后续不会用。
   处置必须走 v3.0 那条判据：**删信息不可逆 → 证据不足时选可逆的动作**（分层加载而非硬删）
3. **成本折算用的是公开单价，不是我真实的账单**——如实标注单价来源与日期
4. **不宣称"通用"**：v4.0 只承诺**从 OTel 口径的 trace 出发**，符合该口径的 agent 都能跑

## 零、定位与护城河（先读这段，防止做偏）

**一句话**：接入数据源，产出经分析可视化的报告，报告上每个数字带
"可信/仅借鉴/不可用"徽章，徽章可点开看归因证据。

- **护城河不是统计检查，是归因证据链**。完整性/唯一性/新鲜度/离群值这些
  通用检查是 Great Expectations / dbt tests / Soda 的主场，我们只把它们
  作为"通用基线包"；差异化在领域包的归因知识：缺 6 行是漏采还是 2022-01
  中信证券配股停牌——这决定徽章是 ✗ 还是 ✓（真实案例见
  `docs/reviews/2026-09-15-attribution.md`）
- **徽章四档，每档可点开看证据**：
  | 徽章 | 含义 | 证据要求 |
  | --- | --- | --- |
  | ✓ 已核验 | 领域知识归因背书 | 归因结论 + 证据引用（公告/事件表/截面共动） |
  | ✓ 基线通过 | 仅通用检查通过，无领域知识参与 | 检查项清单 |
  | ⚠️ 仅借鉴 | 有疑点，人工判断 | 疑点描述（如"近 30 日空值率 0→40%"） |
  | ✗ 不可用 | 归因为真实故障 | 根因 + 建议动作 |
- **多智能体是手段不是卖点**。报告生成有真实分工（采集→分析→可视化→
  可信审校），用现成 Supervisor + nodes 架构；对外叙事的主角是徽章
  与证据链。单 vs 多的 token 账沿用 `eval-agent-single-vs-multi` 的纪律如实归档
- **"任意数据"在 v1 不做承诺**。协议通用（任何数据可跑通用包），智能在
  领域包（首发只有 A 股包）。演示泛化的方式是对比页：同一数据集
  仅通用包 vs +领域包，徽章含金量的差值就是产品本身

## 四·续、Phase R4 · v3.0 Agent 训练数据的质检与过滤（当前主线）

**交付物：`findata-trust-filter` —— 丢进去一批 Agent 轨迹，吐出"哪些能
喂训练、哪些不能、为什么"，每一条判定带证据链。**

### R4.1 轨迹质检层（探针 + 正负样本判定）✅ 已落地

复用 `dq/badges.py` 的徽章实现（单一实现，不另起炉灶），落到轨迹上：

| 判定 | 含义 | 证据要求 |
| --- | --- | --- |
| ✓ 可用正样本 | 路径正确且结果正确 | 关键步骤清单 + 无降级/无重试风暴 |

| ⊘ 不算失败 | 根因为环境（沙箱超时/工具缺失） | 环境证据——**别把它当负样本，会浪费数据** |

  - [x] 48 条真实轨迹跑质检，逐条判定可复核（归档 `examples/agent-trace-report.txt`）
  - [x] loud / silent 两档严重度判定单测钉死（`tests/test_agentops.py`）
  - [x] **误报防线单测钉死**：`ungrounded_slot` 三道防线、`retry_storm`
        改为判「同名**且同参数」——第一版在真实语料上误报 53 条
  - [ ] **归因准确率 ≥ 90%** —— **未达成，刻意保留红灯**（见下）

> **关于那个未打勾的门禁（必须写清楚，不许偷偷划掉）**
> 早先用自造合成集测出 100%，换成从未参与调参的 held-out 集后掉到
> **63.6%**（`tool_missing` 0/20、`env_timeout` 0/20）。这 36 个百分点
> 就是"自己造的样本证明不了自己的规则"的量化代价：规则怎么写的，样本
> 就怎么长。因此 R4.2 的合成管线**整体作废**，改走真实数据路线，而**真实
> 数据没有根因标签，准确率无从计算**——所以这个门禁不是"过了"，是
> **在真实数据口径下无法测**。留着它当素材：面试时能讲清为什么测不了，
> 比报一个 100% 可信得多。

### R4.2 ~~合成管线~~ → **已作废，改走真实数据**

原计划"自己造根因已知的失败样本来测归因器"。**放弃，理由三条**：

1. **循环论证**：规则怎么写的，样本就怎么长。合成集 100% → held-out 63.6%
   已经把这个代价量化了，继续调只会让数字更好看、结论更不可信。
2. **用户明确要求**：真实数据优先，不要模拟或自造。
3. **真实数据已经够用**：`Salesforce/xlam-function-calling-60k` 是公开的
   tool-calling 语料，形状就是轨迹，规模 6 万条，不需要自己造。

`src/findata/agentops/synth.py` 与 `scripts/run_synth_eval.py` 已删除
（代码仍在 git 历史）。**无标签是生产环境的常态**，质检必须能在没有
golden 的前提下工作——`ungrounded_slot` 探针就是为这个设计的。

      （移动）**——统一成一句"补 default"会让数据源方改得更错。同时删掉一个
      全量 2162 命中的类型/默认值冲突探针（查出是表示层约定：89.1% 的
      default 本就是字符串），把这次自我否定写进报告第八节

**最锋利的一条发现**：B 类"必填参数没传"经核查**全都不是 agent 漏填**，
而是工具 schema 的 description 承诺了默认值、schema 里却没标 default。
形态与"agent 能力问题"完全一致，结论相反。第一版就是把它全判成了
`param_error`（改进建议：换更大的模型）——方向完全错。

**第二层（更硬的证据）**：其中 2 项不是"忘写"，是**写错位置**。
`calculate_electric_field` 的原始 schema 里，`permitivity` 的描述称默认值
`8.854e-12`，而该值被标在 `charge` / `distance`（两个都是 `type: int`）上。
8.854e-12 是真空介电常数，不可能是库仑计的电荷量的默认值——**有值落在错误
位置，比"没有值"更难用疏忽解释**。所以"漏了"和"放错了"必须分开处置。

- [x] Windows 上 `resource` 不存在 → 内存限制**标 `memory_limit_applied=False`**，

**边界写在代码与报告里，不吹**：
- 这是**进程级隔离，不是安全沙箱**，防不住恶意代码。要那个得用容器，

却被记成 timeout——**子进程冷启动就要 ~0.4s**。阈值必须留够启动余量。

## 五、诚实边界（本阶段明确不做）

- **不过度承诺"任意数据可信"**：v1 只承诺通用包基线 + 领域包核验，
  徽章必须如实区分"✓ 已核验"与"✓ 基线通过"
- **可信分只对已观测事实归因**，不做预测性声明（"这数据以后会坏"不归我们说）
- **可视化够用即可**：图表服务于报告可读性，不做花哨前端（沿用旧边界）
- **实盘 / 交易信号红线不变**
- **封存模块不投入**：RL 训练等有卡；eval-gate 独立产品线封存
  （其判官校准思想在 R1.3 审校节点中以"无徽章不引用"的形式落地）
