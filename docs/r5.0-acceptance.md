# R5.0 验收记录 · 上下文审计实验台

> 记录于 2026-09-18。对应 `docs/ROADMAP.md` 的 R5.0 门禁。
> 本文件的所有数字分两类，**永不混用**：标「实测」的来自 provider 的
> `usage` 字段或工具的真实返回；标「换算」的明确写出换算口径。
> 一条规矩：**只要一个数字是估的，它就不能和实测数放在同一张表里比大小。**

---

## 0. 这一阶段要证的不是「我搭了一个 agent」

如果交付物是「一个能回答本仓库问题的 agent」，那它一文不值——那是 hello world
的量级。R5.0 的交付物是**一个能产出可复现证据的观测台**，判据只有一条：

> **换一台机器、换一个人，能不能重跑出同一批数字。**

所以这一阶段的验收标准里没有「agent 回答得多好」，只有「数字能不能复现」。
`reset_for_test()` 那个坑（见 §4.1）之所以算 R5.0 的成果，是因为它属于这一类：
**一个让测试"看起来在验证、其实什么都没验证"的缺陷，比一个让测试变红的缺陷危险得多。**

### 1.1 为什么不用 langchain-openai / langgraph（尽管依赖已装、别处也在用）

本项目要算的是**上下文经济学**：必须能逐条说清「这次 `prompt_tokens` 里，哪些是
工具定义贡献的、哪些是工具返回贡献的、哪些是历史重发贡献的」。

框架会往 payload 里加入自己的东西（隐式模板、工具序列化差异、消息重排、重试），
**这些都会混进 `prompt_tokens` 且事后无法剥离**——账单就不可归因了。
手写薄循环的代价是要自己处理 tool loop，收益是每个 token 都有出处。
这条取舍写进了 `llm.py` 的模块 docstring。

## 2. 已实测的数字

### 2.1 工具定义本身吃多少 prompt token（**实测，非换算**）

方法：**同一条消息 payload 发两次，唯一变量是有没有 `tools`**，读上游返回的
`usage.prompt_tokens` 求差。上游本来就在数 token，没有理由自己估。

模型 `qwen2.5:latest`，探测消息一句话，每臂重复 3 次
（`scripts/measure_tools_token_cost.py`）：

| 臂 | 工具数 | prompt_tokens | 相对无工具的增量 | 重复 3 次一致？ |
| --- | --- | --- | --- | --- |
| 无工具 | 0 | 45 | — | ✅ |
| 活跃 | 4 | 613 | **+568** | ✅ |
| 全量 | 27 | 2277 | **+2232** | ✅ |

**核心数字：从 4 个工具换成 27 个工具，仅在工具定义上多花 1664 token/次
（边际 72.3 token/工具）。**

#### 读法警告（先拆掉我自己的虚高陷阱）

上表里「工具定义占本次 prompt 的 92.7% / 98.0%」**不是可迁移的结论**：
探测器里其余部分只有 45 token，是一句话。**占比接近 100% 是短 prompt 的产物，
不是工具定义的一般性质。** 对话越长、工具返回越多，同一批工具定义的占比就越低。

- **可迁移的说法**：这批工具定义固定吃 **2232 token/次**，每轮都重发、与任务无关。
- **要谈占比**，必须同时给出「对话其余部分有多大」，否则等于没给分母。
- 这条警告写进了脚本的 stdout **和** 落盘 JSON 的 `quantities` 字段——
  口径要活在产物里，不能只活在文档里。

### 2.2 模型不匹配的代价是**双向**的（3B vs 7B，同一套 harness）

> ⚠️ **先看这一条的效力**：样本只有 **6 个任务**，配对不一致对 4 对，
> McNemar 精确检验 **p = 0.125，不显著**；token 侧也只是单次观测、没有检验。
> **所以下面这整节是"方向性观察"，不是"已证实的结论"。**
> 要把它变成结论，需要把 3B 也在同样的 32 个任务上跑一遍（n=32）。**这正是
> 下面做的事——见 §2.2.1 的处置。** 我先把这句写在表前面，免得有人只看表。

同一个 runner、同一批 6 个任务、同一份 27 个工具清单，唯一变量是模型：

| | `qwen2.5:3b` | `qwen2.5:latest`（7B） |
| --- | --- | --- |
| 关键词命中 | **0 / 6** | **4 / 6** |
| 轮数 | 13 | 12 |
| 工具调用次数 | 7 | 6 |
| 工具调用异常码 | **7 / 7** | 2 / 6 |
| prompt_tokens 合计 | **30,548** | 28,516 |
| 工具调用结果 | `list_files` ×6 **全部 error**、`read_file` ×1 not_found | `list_files` ×5（4 ok / 1 not_found）、`get_signature` ×1 not_found |

**这张表的信息量在于它的方向与直觉相反**：

- 3B **并没有更便宜**。它多跑了一轮、多调了一次工具，prompt_tokens 反而**更高**
  （30,548 > 28,516），同时把命中率赔到 0。
- 失败原因不是"3B 笨"，是一条很具体的行为：它**连参数名都抄错**——
  `{'path: ': 'src/agentops'}`，**值对、键名错**（带冒号和空格，是抄写痕迹）。
- 这条独立复现了 TSCG 的结论（Phi-4 14B 在 20 个工具下用原始 JSON schema
  准确率 0%）。

**统计上必须说的话**：0/6 与 4/6 看着悬殊，但**4 个不一致对**在符号检验下
只到 p = 0.125 —— **达不到显著**。这不是"结论错了"，是**样本量不够**。
把它写成"3B 差得多"是拿描述当推断，和第 2.1 节那条"占比不能当头条"是同一类错。

**我在这件事上的处置顺序，比结论本身重要**：我先把自己的错误信息改成**可行动的**
（回合法参数名清单，`_valid_param_names` → `call_tool`），**再**去看模型能不能自修。
模型看到正确参数名后仍未自修（重试同一个错键），这时我才有资格说「这个模型不行」。
**错误信息先改对，才有资格说模型不行**——反过来做就是拿模型的锅盖自己的 bug。

> 3B 的失败产物单独留档为 `examples/context-audit/*-3b-smoke.*`，**不删除**。
> 它是"模型不匹配"这一类成本唯一的实测证据。

### 2.2.1 处置：把 3B 也在 32 个任务上跑一遍，让这条有个正经的 n

`p = 0.125` 的直接后果不是"撤掉这一节"，而是**补样本**。两臂全量跑完后追加
第三个臂 `--tools all --model qwen2.5:3b --tag all3b`（工具清单、任务、harness
与 `all7b` 完全相同，**唯一变量仍是模型**），然后用
`scripts/grade_audit_runs.py --arms all7b all3b` 重算配对检验。

**这条同时就是 R5.2「模型路由」那一臂的正式读数**（见 ROADMAP R5.2 的注）。

### 2.2.2 分档判据：关键词命中不能单独承担质量结论

跑全量时暴露的问题，与模型无关，是**判据本身**的问题：7B 的输出是长篇中文
散文，答对了也可能没用指定关键词；反过来，**一次工具都没调却"答对"**的
（拿先验蒙的）关键词判据判不出来。

处置：新增 `scripts/grade_audit_runs.py`，**事后**用分档判据重判落盘的
`final_answer`（所以**不需要重跑**，两臂可比性不受影响）：

| 档位 | 定义 | 用途 |
| --- | --- | --- |
| `hit` | 关键词命中（`tasks.is_hit`） | 保留可比性；**弱判据** |
| `process_ok` | `n_tool_calls > 0` 且 `stopped_reason == answered` | **过程**判据，不是"答对" |
| `verified_hit` | `hit` AND `process_ok` | **这一档才可以对外说** |
| 可疑档 | `hit` 但 NOT `process_ok` | "可能蒙对"，**单独计数，不并入任一边** |

三档**分开报**，不给单一"准确率"——沿用 v3.0 的处置纪律：不把混合体报成一个数。
另有 `tool_parse_errors` 单独计数（模型连 JSON 都没吐对），与 `result_code=error`
（工具执行后报错）**分开**，否则会把"模型不会用工具"和"工具没找到东西"
算成同一件事。

6 任务冒烟上的读数（同一份 grader）：

| 臂 | hit | process_ok | verified_hit | 工具调用异常码 | 解析失败 |
| --- | --- | --- | --- | --- | --- |
| `3b-smoke` | 0/6 | 6/6 | 0/6 | 7 / 7 | 0 |
| `7b-smoke` | 4/6 | 6/6 | 4/6 | 2 / 6 | 0 |

**注意 `process_ok` 两边都是 6/6**：3B 虽然在参数名上全错，但它**确实调了工具、
也确实正常收尾**了——所以它的问题在 `hit` 这一档，不在过程。这个区分有用：
它说明 3B 的失败是**参数构造**问题，不是"不肯干活"。

### 2.3 复现性自检

- 同一 payload 连发 3 次，`prompt_tokens` **逐次完全相等**（三臂全部通过）。
  不等就说明这个量不可复现，那后面所有「省了 X%」都不用看了。
- 字符数是确定性量，进断言（`tests/test_contextbudget.py`）。
- 两个量的关系是「都有用，但不许互相冒充」：报告里说「某工具返回占 X token」时，
  那个 X 必须是实测的，不是用字符数除系数估的。

工具清单规模（**字符口径**，确定性量，用于回归而非对外报数）：
27 个工具定义 = **11,559 字符/次**，每轮重发。

- span 名：`gen_ai.chat` / `gen_ai.tool.call`。

  `gen_ai.tool.result_code` / `gen_ai.usage.input_tokens` /
  `gen_ai.usage.output_tokens` / `gen_ai.request.model`。
- 本项目自有量一律走 **`findata.context.*`** 前缀（`messages_chars` /

- 为什么坚持这个前缀：下游会把 `gen_ai.*` 当**规范字段**解析。混进去会让别人对我

## 4. 已知缺口（主动暴露，不是"以后再说"）

### 4.1 【最重要】工具返回**原文没有归档** → R5.1 的核心指标现在测不了

我原本给 R5.1 定的核心指标是「**被后续引用的字段集 vs 从未被引用的字段集**」。
搭完 R5.0 才发现：**当前数据模型测不了这件事。**

- runner 只记了每次工具返回的 `payload_chars`，**没有记返回内容**；
- 即使记了原文，现在的工具返回的是**散文式文本**（markdown 片段），
  没有"字段"这个粒度——无法回答"这个字段被引用了吗"。

**所以 R5.1 必须先做一次数据模型改造**，不是直接开始分析：

1. 工具返回改成**结构化**（有名字的字段），并对每个字段记录自己的字符数；
2. 保留**可判定"是否被引用"的最小信息**——不是留全文（PII + 体积），
   而是留字段级摘要 / 值指纹，让"后续消息里出现过这个字段的值"可判定；
3. 判据要分层：**「观测到从未被引用」是强证据**（模型在这些任务里确实没用），
   **「本批任务没用到」是弱证据**（可能只是任务不覆盖）。

**这条缺口是我主动写下来的，因为它决定了 R5.1 的第一件事是改模型而不是跑分析。
不写下来，下一阶段就会拿着 `payload_chars` 去硬编一个"字段利用率"，那是指标造假。**

### 4.2 `SILENT_TOOLS` 是构造的，不是真实 MCP server 的工具清单

23 个沉默工具的手写定义，用来给"工具膨胀"造自变量。因此：

> 任何基于这批定义得出的**比例**，只能算"实验条件下的量"，**不能当行业事实引用**。

这条标注写在 `schemas.py` 的 docstring 里（口径进产物，不进嘴）。
§2.1 的 **token 绝对增量**受这条影响较小（它测的是"定义文本长度 → token"这个映射，
映射本身是真的）；受影响的是一切"占比"类说法。

### 4.3 一次超时：t08（`ReadTimeout`，224.1s，工具返回 8,528 字符）

- 这一条**不是模型能力问题**，是本地推理在长 payload 下的超时。
- 两臂对比时要**同口径处理**：要么两边都按"环境失败"排除，要么两边都保留并标注。
  **不许只把对自己不利的那一臂的超时剔掉。**
- 更广的诚实边界：本机 7B 模型，**token 侧结论可迁移**（token 数由上下文结构决定，
  与模型无关），**成功率侧只在本地口径下成立**（小模型对上下文噪声更敏感）。

### 4.4 一个被测出来的既有缺陷：`reset_for_test()` 的声明与实现不符

搭实验台时撞出来的，已修（提交 `5f2e495`）。

- 原 docstring 写「让每个 test 从干净状态起跑」，但 OTel 的 TracerProvider 是
  **进程级单例**：清掉模块缓存后 `setup_tracer()` 新建的 provider 会被 SDK 忽略，
  span 继续导进**旧** exporter，而 `get_in_memory_exporter()` 返回**新** exporter。
- 后果是测试**看起来在验证，其实什么都没验证**。当时的表现是一个 `IndexError`，
  **真凶是不一致，不是空列表那么简单**——这也是它藏得住的原因。
- 现在它只做能做的事（清空当前缓冲），且**刻意不动** `_INITIALIZED` / `_PROVIDER`；
  新增回归测试用**身份断言**钉住那条不变量。
- 通用教训：**「静默不验证」只能靠身份断言抓，靠数值断言抓不到。**

### 4.5 【会影响 R5.2 结论】当前的质量判据太弱，撑不起"成功率变化"

跑全量时看到的现象：`all` 臂前 20 个任务只命中 3 个，而同一套任务在 6 任务
冒烟里是 4/6。差额不是模型忽好忽坏，是**判据太窄**：

- `must_contain` 要求答案里出现**指定关键词**，而 7B 的输出是长篇中文散文，
  就算答对了也可能没用那个词；
- 反例也确实存在：t10 **一次工具都没调**（`calls=0`）却"answered"，
  它是拿先验答的——这类**该判失败**的，弱判据判不出来。

**所以「关键词命中」绝不能承担 R5.2 的"成功率变化"。** 它的正确用途只有两个：
①两臂用**同一把尺**做相对比较；②作为"明显崩坏"的粗筛。

**好消息是这一步不需要重跑。** `runs-<tag>.jsonl` 里存了 `final_answer` 原文
（R5.0 的一个设计决定），所以更强的判据可以**事后**套用在同一批答案上，
两臂的可比性不受影响。R5.1/R5.2 之前必须做掉这件事，候选方向：

1. 把任务判据从"出现关键词"改成"**出现精确值**"（真实答案里的数字/路径/标识符），
   并对每个任务写明"可接受的等价写法有哪几种"；
2. 补一条**过程判据**：`calls == 0` 而任务要求查仓库的，直接判失败
   （t10 那类现在是漏网的）；
3. 若要引入模型判定，必须**同时报人工/机器一致性**——v3.0 的 Q 系列里
   "人工一致性 κ 没做"是已经承认过的洞，不能在这里换个地方重犯。

## 6. 与 v3.0 的关系

**不是推翻，是同一动作换域。** v3.0 问「这条轨迹能不能喂训练」，
v4.0 问「这段内容该不该进上下文」——都是**准入决策**。v3.0 的产物
（`agentops/triage.py` 的五档处置、`RULES_VERSION`、可复现三元组、
文档一致性门禁）在本阶段**继续有效**，且 R5.1/R5.2 的处置纪律直接沿用它的判据：

> 处置不只看「有多可疑」，还看 **①能不能给出可执行动作 ②队列长度**。

这也解释了为什么 R5.2 的产物必须是「**一条具体的、可重放的裁剪建议**」，
而不是「一份分析报告」——报告的处置动作不可执行，那正是我在
`docs/competitive-landscape.md` 里判定「产物形态弱」的原因。
